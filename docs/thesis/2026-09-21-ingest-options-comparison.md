# ร่างหัวข้อ — การเปรียบเทียบทางเลือกสำหรับการนำเข้าข้อมูลผู้สมัครโดยอัตโนมัติ

สำหรับวางในหัวข้อ "งานต่อยอด" ของบทผลการทดสอบ หรือแยกเป็นหัวข้อหนึ่งในบทสรุป
ตามที่อาจารย์ที่ปรึกษาเห็นควร

**เขียน 21 ก.ย. 2569** · ข้อมูลราคาและคำพิพากษาตรวจสอบกับแหล่งอ้างอิง ณ วันที่เขียน
**ราคาและสถานะของบริการเปลี่ยนได้ ควรตรวจซ้ำก่อนอ้างอิงในการนำไปใช้จริง**

---

## บทนำของหัวข้อ

ระบบที่พัฒนาขึ้นรองรับการนำเข้าข้อมูลผู้สมัครสามเส้นทาง ได้แก่ การอัปโหลดไฟล์ CSV
ด้วยตนเอง การค้นหาด้วยเทคนิค X-ray ผ่านเครื่องมือค้นหา และการดึงข้อมูลอัตโนมัติ
ตามกำหนดเวลา โดยเส้นทางที่สามได้พัฒนากลไกไว้ครบถ้วนแล้วแต่**ยังไม่ได้เปิดใช้งาน**
ในเวอร์ชัน 1.0.0

หัวข้อนี้อธิบายทางเลือกสามทางที่ได้ประเมิน เหตุผลที่ยังไม่เปิดใช้งาน และแนวทาง
ที่เสนอสำหรับการพัฒนาต่อ

---

## 1. PhantomBuster — ทางเลือกแรกที่พัฒนาไว้

ระบบพัฒนากลไกสำหรับเส้นทางนี้ไว้ครบ ประกอบด้วยสคริปต์ดึงข้อมูล ตารางบันทึกที่มา
(`ingest_runs`) คิวรอการตรวจสอบ (`pending_candidates`) รายชื่อระงับตามคำขอ
(`suppressed_profiles`) และกำหนดการทำงานอัตโนมัติผ่าน GitHub Actions

**เหตุผลที่ไม่เดินต่อ** บริการนี้ทำงานโดยใช้เซสชันของบัญชี LinkedIn ของผู้ใช้เอง
ซึ่งมีความเสี่ยงที่บัญชีจะถูกระงับ และเมื่อทดลองค้นหาด้วยบัญชีที่สร้างใหม่
ผลลัพธ์ที่ได้แสดงเป็น "LinkedIn Member" ทั้งหน้า คือไม่มีทั้งชื่อและลิงก์โปรไฟล์
เนื่องจากแพลตฟอร์มจำกัดการมองเห็นตามเครือข่ายความสัมพันธ์ของบัญชีที่ล็อกอิน
ข้อมูลที่ได้จึงไม่สามารถนำมาใช้ได้

---

## 2. X-ray Search — ทางเลือกที่นำมาใช้จริง

เทคนิคนี้ใช้ตัวดำเนินการค้นหาของ Google จำกัดขอบเขตเฉพาะหน้าโปรไฟล์
(`site:th.linkedin.com/in`) ร่วมกับเงื่อนไขตำแหน่งงานและสถาบันการศึกษา

**ข้อได้เปรียบที่ทำให้เลือกใช้** ดัชนีของเครื่องมือค้นหาไม่ขึ้นกับเครือข่ายของผู้ใช้
จึงแสดงชื่อและลิงก์โปรไฟล์ได้ทุกรายการ ซึ่งแก้ข้อติดขัดของทางเลือกแรกได้โดยตรง

**ข้อจำกัดที่ทำให้ทำอัตโนมัติไม่ได้** ผลการค้นหาเป็นข้อความก้อนเดียวที่ไม่มีป้าย
ระบุฟิลด์ รูปแบบต่างกันในแต่ละรายการ และถูกตัดให้สั้นเสมอ **สิ่งที่ขาดและสำคัญที่สุด
คือวันที่** ทำให้ไม่สามารถคำนวณจำนวนปีประสบการณ์ได้ ผู้สมัครที่นำเข้าด้วยวิธีนี้
จึงถูกตัดออกจากการกรองด้วยเงื่อนไขประสบการณ์ขั้นต่ำทุกครั้ง

ระบบจึงนำเทคนิคนี้มาใช้เป็น**เครื่องมือช่วยค้นหา** ไม่ใช่ท่อส่งข้อมูลอัตโนมัติ
กล่าวคือระบบสร้างคำค้นให้ผู้ใช้นำไปเปิดดูเอง แล้วกรอกข้อมูลลงแบบฟอร์มมาตรฐาน

**ข้อจำกัดด้านความยั่งยืน** ช่องทางแบบโปรแกรมของเครื่องมือค้นหาปิดตัวไปแล้ว
ทั้งสองราย โดย Google Custom Search JSON API ระบุในเอกสารว่าปิดรับลูกค้าใหม่
และมีกำหนดยุติบริการ ส่วน Bing Search API ถูกยกเลิกไปแล้ว การทำอัตโนมัติผ่าน
เส้นทางนี้จึงเหลือเพียงการใช้บริการตัวกลางซึ่งขัดข้อกำหนดของเครื่องมือค้นหาเอง

## 3. Bright Data — แนวทางที่เสนอสำหรับการพัฒนาต่อ

บริการนี้ดึงข้อมูลจากหน้าสาธารณะโดย**ไม่ต้องใช้บัญชีของผู้ใช้** จึงไม่มีความเสี่ยง
ที่บัญชีจะถูกระงับ และไม่ประสบปัญหาการจำกัดการมองเห็นตามเครือข่ายเหมือนทางเลือกแรก

**สถานะทางกฎหมายที่ต่างจากทางเลือกอื่น** มีคำพิพากษาของศาลสหรัฐอเมริกาสองคดี
ที่เกี่ยวข้องโดยตรง

- **Meta Platforms v. Bright Data** (มกราคม 2567) ศาลแขวงภาคเหนือของรัฐแคลิฟอร์เนีย
  วินิจฉัยว่าข้อกำหนดการใช้งานของแพลตฟอร์มไม่อาจตีความให้ครอบคลุมการเก็บข้อมูล
  สาธารณะโดยผู้ที่**ไม่ได้เข้าสู่ระบบ**
- **X Corp. v. Bright Data** (พฤษภาคม 2567) ศาลยกฟ้อง โดยระบุว่าแพลตฟอร์มไม่อาจ
  อ้างสิทธิ์เหนือการเข้าถึงหน้าสาธารณะของตน และข้อกล่าวหาเรื่องการทำซ้ำข้อมูล
  สาธารณะถูกแทนที่ด้วยหลักกฎหมายลิขสิทธิ์

**คำสำคัญของทั้งสองคดีคือสถานะ "ไม่ได้เข้าสู่ระบบ"** คำพิพากษาเหล่านี้ไม่ได้
รับรองว่าการเก็บข้อมูลอัตโนมัติทุกรูปแบบชอบด้วยกฎหมาย แต่วินิจฉัยว่าข้อกำหนด
การใช้งานไม่ผูกพันผู้ที่ไม่ได้เข้าสู่ระบบ ซึ่งเป็นจุดที่ทางเลือกแรกอยู่ตรงข้ามพอดี
เพราะทำงานในสถานะที่เข้าสู่ระบบแล้ว

**ความพร้อมของระบบในการรองรับ** โครงสร้างของระบบแยกส่วนที่ติดต่อกับผู้ให้บริการ
ภายนอกออกเป็นไฟล์เดียว (`lib/ingest/phantombuster.ts`) ตั้งแต่ตอนออกแบบ
โดยมีเจตนาให้การเปลี่ยนผู้ให้บริการกระทบเฉพาะไฟล์นั้น ส่วนกลไกที่เหลือทั้งหมด
ได้แก่ การตรวจรายชื่อระงับก่อนบันทึก การคัดกรองข้อมูลไม่ครบเข้าคิว และการข้าม
รายการที่ไม่มีการเปลี่ยนแปลงด้วยค่าแฮช สามารถใช้ต่อได้โดยไม่ต้องแก้ไข

**ข้อจำกัดด้านความครบของข้อมูลที่ต้องระบุไว้** เอกสารของผู้ให้บริการเองระบุว่า
ตั้งแต่วันที่ 13 พฤศจิกายน 2568 แพลตฟอร์มต้นทางได้จำกัดการเข้าถึงข้อมูลส่วน
ตำแหน่งงาน ประสบการณ์ และการศึกษาของหน้าสาธารณะ ทำให้อัตราการได้ข้อมูลของ
สามส่วนนี้ลดลงจากประมาณร้อยละ 50-64 เหลือประมาณร้อยละ 2 **สามส่วนดังกล่าว
คือส่วนที่เกณฑ์คัดกรองของระบบต้องใช้** ผลที่ตามมาคือรายการส่วนใหญ่จะถูกส่งเข้า
คิวรอการตรวจสอบแทนที่จะบันทึกเข้าฐานข้อมูลโดยตรง ซึ่งลดประโยชน์ของการทำงาน
อัตโนมัติลงอย่างมีนัยสำคัญ **ข้อได้เปรียบด้านสถานะทางกฎหมายจึงไม่ได้แปลว่า
ได้เปรียบด้านคุณภาพข้อมูล** และเป็นเหตุผลว่าทำไมจึงเสนอไว้เป็นแนวทางพัฒนาต่อ
มากกว่าจะสรุปว่าเป็นทางเลือกที่ดีกว่า

**ข้อจำกัดที่พบจากการทดลองจริง** การทดลองเรียกใช้บริการเมื่อวันที่ 22 กันยายน
2569 ไม่สำเร็จ เนื่องจากผู้ให้บริการตอบกลับด้วยสถานะว่าบัญชียังไม่ผ่านการยืนยัน
ตัวตน การเข้าถึงชุดข้อมูลที่เกี่ยวกับบุคคลจึงถูกกั้นไว้หลังกระบวนการตรวจสอบ
ผู้ใช้บริการ **ข้อเท็จจริงนี้มีนัยสำคัญเชิงวิเคราะห์มากกว่าการเป็นอุปสรรคทางเทคนิค**
เพราะแสดงว่าแม้ผู้ให้บริการที่มีคำพิพากษารองรับสถานะของตน ก็ยังวางมาตรการควบคุม
ผู้ใช้บริการของตนเองอีกชั้นหนึ่ง การเก็บข้อมูลส่วนบุคคลโดยอัตโนมัติจึงไม่ใช่สิ่งที่
กระทำได้โดยอิสระเพียงเพราะข้อมูลเปิดเป็นสาธารณะ แต่อยู่ภายใต้การควบคุมทั้งจาก
ผู้ให้บริการและจากกฎหมายคุ้มครองข้อมูลส่วนบุคคล ซึ่งสอดคล้องกับข้อพิจารณา
ในหัวข้อถัดไป

## 4. เหตุผลที่ยังไม่เปิดใช้งานการดึงข้อมูลอัตโนมัติในเวอร์ชันนี้

แม้ทางเลือกที่สามจะมีความเป็นไปได้สูงทั้งด้านเทคนิคและค่าใช้จ่าย แต่ยังมีเงื่อนไข
ที่ยังไม่ได้แก้ไข ซึ่งเป็นเงื่อนไขด้านการคุ้มครองข้อมูลส่วนบุคคล ไม่ใช่ด้านเทคนิค

**คำพิพากษาที่อ้างถึงเป็นเรื่องสัญญาและลิขสิทธิ์ตามกฎหมายสหรัฐอเมริกา
ไม่ได้เกี่ยวกับพระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคลของไทย** การที่การเก็บข้อมูล
ไม่ขัดข้อกำหนดของแพลตฟอร์ม ไม่ได้ทำให้หน้าที่ตามมาตรา 25 หมดไป กล่าวคือเมื่อเก็บ
ข้อมูลจากแหล่งอื่นที่ไม่ใช่เจ้าของข้อมูล ผู้ควบคุมข้อมูลยังคงมีหน้าที่แจ้งเจ้าของ
ข้อมูลภายในสามสิบวัน ซึ่งระบบยังไม่มีกลไกรองรับ

นอกจากนี้ ส่วนที่ติดต่อกับผู้ให้บริการภายนอกยังไม่เคยได้รับการตรวจสอบกับ
บริการจริง เนื่องจากยังไม่มีบัญชีผู้ใช้ รูปแบบข้อมูลที่ได้รับจึงยังเป็นการอนุมาน
จากเอกสารประกอบเท่านั้น

**การเปิดใช้งานก่อนที่กลไกการแจ้งตามมาตรา 25 จะพร้อม จะทำให้ระบบขัดกับหลักการ
ที่ตัวเองประกาศไว้ในหัวข้อการคุ้มครองข้อมูลส่วนบุคคล** ผู้พัฒนาจึงเลือกพัฒนา
กลไกรองรับไว้ให้ครบ แต่ปิดการทำงานไว้ และบันทึกเหตุผลไว้อย่างชัดเจนแทน

## 5. ข้อเสนอสำหรับการพัฒนาต่อ

1. เชื่อมต่อบริการดึงข้อมูลที่ทำงานโดยไม่ต้องใช้บัญชีผู้ใช้ และทดสอบรูปแบบข้อมูล
   ที่ได้รับจริงกับตัวแปลงข้อมูลที่มีอยู่
2. **พัฒนากลไกแจ้งเจ้าของข้อมูลตามมาตรา 25 ก่อนเปิดใช้งาน** โดยอาจเป็นการส่ง
   หนังสือแจ้งทางอิเล็กทรอนิกส์พร้อมช่องทางการใช้สิทธิ์ตามมาตรา 33
3. ทดสอบด้วยชุดข้อมูลขนาดเล็กในสภาพแวดล้อมสำหรับการพัฒนาเท่านั้น ก่อนนำไปใช้
   กับระบบที่เปิดให้บริการจริง
4. เปิดกำหนดการทำงานอัตโนมัติเมื่อผ่านข้อ 1 ถึง 3 แล้ว

## หมายเหตุสำหรับผู้เขียนเล่ม

- **หัวข้อนี้ตอบคำถามที่กรรมการมีโอกาสถามสูงที่สุดข้อหนึ่ง** คือ "ทำไมฟีเจอร์นี้
  ถึงไม่เสร็จ" — คำตอบที่แสดงว่าประเมินทางเลือกครบแล้วและเลือกไม่เดินด้วยเหตุผล
  ที่ชัดเจน หนักแน่นกว่าการยอมรับว่าทำไม่ทัน
- **ชื่อผู้ให้บริการควรปรากฏในเล่ม** เพราะเป็นข้อเท็จจริงที่ตรวจสอบได้ แต่ควร
  ระบุวันที่ที่ตรวจสอบข้อมูลกำกับไว้ด้วย เนื่องจากราคาและสถานะของบริการเปลี่ยนแปลงได้
- **ควรใส่เชิงอรรถอ้างอิงคำพิพากษาทั้งสองคดี** พร้อมปีที่ตัดสิน ผู้อ่านที่ต้องการ
  ตรวจสอบจะหาได้จากชื่อคดี
- **อย่าเขียนให้อ่านเหมือนการรับรองว่าการเก็บข้อมูลอัตโนมัติถูกกฎหมายในประเทศไทย**
  — ข้อความในหัวข้อ 4 เขียนไว้ให้ชัดแล้วว่าคำพิพากษาที่อ้างถึงเป็นคนละเรื่องกับ PDPA
  ถ้าตัดย่อหน้านั้นออก ความหมายของทั้งหัวข้อจะเปลี่ยนไปในทางที่ผิด
