# 1. ER Diagram (หัวข้อ 3.5)

## ปัญหาที่ต้องตัดสินใจก่อนวาด

ของจริงมี **16 ตาราง** ยัดลงหน้า A4 เดียวแล้วอ่านไม่ออกแน่นอน
(แก้จำนวนเมื่อ 2026-10-20 · จำนวนความสัมพันธ์ให้นับจากภาพที่วาดจริง ไม่ใช่จากตัวเลขที่พิมพ์ค้างไว้)
เล่มเดิมมี 10 ตารางซึ่งพอดีหนึ่งหน้า แต่ไม่ตรงกับของจริง

**ทางที่แนะนำ: แบ่งเป็น 2 ภาพ** ใส่ในเล่มทั้งคู่

- **ภาพที่ 3-11 (ก) ER Diagram ส่วนหลัก** — ผู้ใช้ ผู้สมัคร และการจับคู่งาน
  คือส่วนที่ตอบวัตถุประสงค์ของโครงงานโดยตรง
- **ภาพที่ 3-11 (ข) ER Diagram ส่วนสนับสนุน** — การนำเข้าข้อมูล การประเมินตัวเอง
  และการตามรอย

ทางเลือกอื่นคือวาดรวมภาพเดียวแนวนอนเต็มหน้า ซึ่งอ่านได้แต่ตัวหนังสือจะเล็กมาก

# 2. Use Case Diagram (หัวข้อ 3.2)

## สรุปสิ่งที่เปลี่ยน

| เดิมในเล่ม | ทำอย่างไร |
|---|---|
| 1. เข้าสู่ระบบ | คงไว้ |
| 2. จัดการข้อมูลผู้ใช้ | คงไว้ (Admin) |
| 3. ดึงข้อมูล API | คงไว้ แต่เปลี่ยนผู้กระทำเป็น `data_manager` และเพิ่มความสัมพันธ์ `«extend»` ไปยัง "ตรวจสอบคิวข้อมูล" |
| 4. สั่ง AI วิเคราะห์ข้อมูล | **เปลี่ยนชื่อ** → "ประเมินความเหมาะสมของผู้สมัคร" (ข้อ 10 ของรายการแก้เอกสาร) |
| 5. อัปเดตข้อมูลแดชบอร์ด | คงไว้ |
| 6. ตั้งค่าข้อมูลส่วนตัว | คงไว้ (ตอนนี้เปลี่ยนได้ทั้งชื่อและรหัสผ่านจริงแล้ว) |
| 7. ค้นหา/คัดกรอง | คงไว้ |
| 8. บุ๊คมาร์คคนที่สนใจ | **ยุบรวมกับข้อ 9** → "จัดการ Shortlist" (ข้อ 9 ของรายการแก้เอกสาร) |
| 9. สร้าง Grouplist | **ลบ** (รวมเข้าข้อ 8 แล้ว) |
| 10. ดูข้อมูลผ่านแดชบอร์ด | คงไว้ |
| — | **เพิ่ม** "ประเมินโปรไฟล์ของตนเอง" (ข้อ 12) |
| — | **เพิ่ม** "จัดการตำแหน่งงาน" — ตัดสินแล้ว 18 ก.ย. ให้ใส่ |
| — | **เพิ่ม** "ระงับข้อมูลตามคำขอของเจ้าของข้อมูล" — ตัดสินแล้ว ใส่เฉพาะส่วนนี้ |
| — | **เพิ่ม** "ตรวจสอบคิวข้อมูลนำเข้า" — ใส่ แต่ต้องกำกับว่ายังเปิดใช้งานไม่ได้ |

> ✅ **ตัดสินแล้วเมื่อ 18 ก.ย. 2569 หลังทำ UAT เสร็จ**
>
> **จัดการตำแหน่งงาน — ใส่** เล่มมีตาราง `Job_Posting` และ `Matching_Results`
> ในหัวข้อ 3.6 อยู่แล้ว แต่ไม่มี Use case ว่าใครสร้าง แก้ไข หรือลบตำแหน่งงาน
> ทั้งที่ระบบทำได้ครบ มีประตูสิทธิ์กั้นที่ระดับ `data_manager` และ**ถูกทดสอบไปแล้ว
> 11 กรณี (JB-01 ถึง JB-11) ผ่านทั้งหมด** การไม่มี Use case จะทำให้บทที่ 3
> ขัดกับบทผลการทดสอบของตัวเอง
>
> **แยก "ตรวจคิว" ออกจาก "ระงับตามคำขอ" เป็นคนละ Use case** เดิมเสนอรวมเป็นข้อเดียว
> แต่**ผล UAT แสดงว่าสองอย่างนี้มีสถานะต่างกันสิ้นเชิง**
>
> | | สถานะจริง | หลักฐาน |
> |---|---|---|
> | ระงับตามคำขอ | ใช้งานได้จริง | DM-05 และ DM-09 ผ่าน |
> | ตรวจสอบคิว | **ยังเปิดใช้งานไม่ได้** | DM-10 · DM-11 · บทผลการทดสอบข้อ 4.2 |
>
> คิวรอตรวจเติมได้จากสคริปต์ดึงข้อมูลอัตโนมัติทางเดียว ซึ่งยังปิดอยู่เพราะไม่มี
> บัญชีบริการภายนอก **รวมสองอย่างไว้ในกล่องเดียวจะทำให้ Use Case Diagram บอกว่า
> ทั้งก้อนใช้งานได้ ซึ่งขัดกับบทผลการทดสอบ** และผู้อ่านจะเชื่อภาพมากกว่าตัวหนังสือ
>
> **กล่อง "ตรวจสอบคิวข้อมูลนำเข้า" ต้องมีหมายเหตุกำกับในคำบรรยายใต้ภาพ** ว่า
> เป็นกลไกที่พัฒนาแล้วแต่ยังเปิดใช้งานไม่ได้ในเวอร์ชันนี้ อ้างอิงบทผลการทดสอบข้อ 4.2
> — **ห้ามใส่หมายเหตุลงในกล่องเอง** เพราะจะทำให้ภาพรก และ Use Case Diagram
> มีไว้บอกว่า "ใครทำอะไรได้บ้าง" ไม่ใช่สถานะการพัฒนา

> **สิ่งที่ต้องแก้ตอนวาดจริงใน draw.io**
>
> - เปลี่ยนกล่องสี่เหลี่ยมมนเป็น **วงรี** ตามมาตรฐาน UML
> - เปลี่ยนวงกลมเป็น **รูปคน (stick figure)**
> - ใส่ **กรอบสี่เหลี่ยมรอบ Use case ทั้งหมด** พร้อมชื่อระบบที่ขอบบน
>   (System Boundary) — Mermaid วาด `subgraph` ให้แล้วแต่หน้าตาไม่ใช่ UML
> - ลากเส้น **generalization (หัวลูกศรสามเหลี่ยมโปร่ง)** จาก `data_manager`
>   ไปยัง `member` และจาก `admin` ไปยัง `data_manager`
>   **ข้อนี้สำคัญและเล่มเดิมไม่มี** เพราะระบบใช้สิทธิ์แบบลำดับชั้นจริง —
>   `admin` ทำทุกอย่างที่ `member` ทำได้ ถ้าไม่วาด generalization จะต้องลากเส้น
>   จาก actor ทั้งสามไปยัง use case เดียวกันซ้ำสามรอบ ภาพจะรกและสื่อผิดว่า
>   เป็นสิทธิ์คนละชุดที่บังเอิญเหมือนกัน

>

>    "ให้คะแนน"** การจัดอันดับเป็นคณิตศาสตร์ของเวกเตอร์ล้วนๆ ไม่มี AI
>    เป็นเหตุผลที่ระบบอยู่ในโควตาฟรีได้แม้ผลการค้นหามีหลายสิบคน
> 2. **กิ่ง "AI ล้มเหลว → ถอยไปใช้คำค้นหาดิบ"** ชิปเป็นของเสริม ไม่ใช่แกน —
>    เสียชิปยังค้นเจอ เสียการจัดอันดับคือใช้งานไม่ได้เลย
> 3. **"รวมตัวกรอง" ไม่ใช่ "เขียนทับ"** AI ห้ามลบตัวกรองที่ผู้ใช้ตั้งเอง และ
>    ชิปของ AI รอบก่อนต้องถูกถอดออก ไม่งั้นชิปจากคำค้นหาที่เลิกใช้แล้วจะติดค้าง
>    แล้วกรองผลลัพธ์ทิ้งโดยไม่มีอะไรบอก
> 4. **การกรองเกิดใน SQL ก่อนการจัดอันดับ** ไม่ใช่กรองผลลัพธ์ทีหลัง —
>    ถ้าจัดอันดับก่อนแล้วกรอง ผลที่ได้จะไม่ครบ 20 อันดับที่ตรงเงื่อนไข
> 5. **"ไม่พบผู้สมัคร" กับ "ค้นหาไม่ได้" เป็นสองกิ่งที่แยกกัน** (C3 กับ C4)
>    เคยรวมเป็นกิ่งเดียวแล้วระบบค้นหาพังสนิทโดยหน้าจอขึ้นว่าไม่พบผลลัพธ์
>    **ความแตกต่างนี้คือตัวอย่างที่เขียนในเล่มได้ดี** เพราะเป็นข้อผิดพลาดที่พบจริง
>    แล้วแก้ด้วยการออกแบบ ไม่ใช่การเพิ่มโค้ด

> **วงย้อนกลับ C5 → B5 คือสิ่งที่ทำให้ไดอะแกรมนี้ไม่ใช่ท่อตรง** — ผู้ใช้แก้ชิป
> หรือแก้คำอธิบายแล้วระบบค้นหาใหม่ทันที **โดยไม่เรียก AI อีก** เพราะตัวกรอง
> มาจากมือผู้ใช้แล้ว เส้นนี้จึงกลับไปที่ B5 ไม่ใช่ B2 · ถ้าวาดกลับไปที่ B2
> ภาพจะบอกว่าระบบเสียค่าเรียก AI ทุกครั้งที่แก้ชิป ซึ่งไม่จริง
