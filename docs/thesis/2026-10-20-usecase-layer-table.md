# ตารางเชื่อมโยง Use Case กับชั้นสถาปัตยกรรม (ผู้ใช้ · Front-end · Back-end · ฐานข้อมูล)

ใช้แทนการวาดภาพไม่ได้ **แต่ใช้เป็นต้นแบบตอนลากเส้นได้** และใช้เป็นตารางในเล่มได้เลย
ทุกบรรทัดอ่านจากซอร์สโค้ดจริงเมื่อ 2026-10-20 ไม่ใช่จากการออกแบบที่ตั้งใจไว้

> ⚠ **อ่านก่อนวางลงเล่ม — ตารางนี้ไม่ใช่ Use Case Diagram**
>
> Use Case Diagram ตามมาตรฐาน UML **ไม่มีชั้น Front-end / Back-end / ฐานข้อมูล**
> มันบอกแค่ "ใครทำอะไรได้" กับความสัมพันธ์ `include` / `extend` / `generalization`
> การใส่ชั้นเทคนิคลงไปในภาพนั้นคือการผสม Use Case Diagram กับ Sequence Diagram
> ซึ่งกรรมการที่ดูมาตรฐานจะทักได้
>
> **วางตารางนี้ที่หัวข้อ 3.1 (System Architecture) หรือเป็นหัวข้อย่อยใหม่
> ต่อจาก 3.3 ไม่ใช่ใต้ภาพ 3.2** · ส่วนภาพ 3.2 ให้ใช้รายชื่อ Use case และเส้น
> ความสัมพันธ์จากส่วนที่ 1 และ 4 ของไฟล์นี้ (ตรงกับ source ใน `2026-09-09-diagram-guide.md`)

## ส่วนที่ 1 — ผู้กระทำ (Actors)

| Actor | ค่าในฐานข้อมูล | ทำอะไรได้ |
|---|---|---|
| ผู้ใช้ทั่วไป | `profiles.role = 'member'` | ค้นหา ประเมิน จัดการ Shortlist ดูแดชบอร์ด ตั้งค่าตนเอง ประเมินตัวเอง |
| ผู้จัดการข้อมูล | `profiles.role = 'data_manager'` | ทุกอย่างของ member **+** นำเข้าข้อมูล ระงับตามคำขอ ตรวจคิว จัดการตำแหน่งงาน |
| ผู้ดูแลระบบ | `profiles.role = 'admin'` | ทุกอย่างของ data_manager **+** จัดการผู้ใช้และอนุมัติบัญชี |

**สิทธิ์เป็นลำดับชั้นจริงในโค้ด** (`ROLE_RANK` ใน `lib/auth/session.ts`:
`member` 1 < `data_manager` 2 < `admin` 3) จึงต้องลากเส้น **generalization**
หัวลูกศรสามเหลี่ยมโปร่ง จาก `data_manager` → `member` และ `admin` → `data_manager`
**ห้ามลากเส้นจาก actor ทั้งสามไปยัง use case เดียวกันซ้ำสามรอบ** จะสื่อผิดว่า
เป็นสิทธิ์คนละชุดที่บังเอิญเหมือนกัน

## ส่วนที่ 2 — ตารางหลัก 12 Use Case × 4 ชั้น

สัญลักษณ์ในคอลัมน์ Back-end: **(—)** = ไม่มีโค้ดฝั่งเซิร์ฟเวอร์ของเราในเส้นทางนี้
หน้าเว็บคุยกับฐานข้อมูลตรง (ดูคำอธิบายในส่วนที่ 3 · **ข้อนี้สำคัญ ห้ามตัดทิ้ง**)

### 1. เข้าสู่ระบบ

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | กรอกอีเมลและรหัสผ่าน กดเข้าสู่ระบบ |
| Front-end | `app/(auth)/login/page.tsx` ส่งให้บริการยืนยันตัวตนของ Supabase (GoTrue) แล้ว**อ่านบทบาทและสถานะบัญชีของตนเองต่อทันที** · ถ้าไม่ผ่านด่านจะออกจากระบบและแสดงเหตุผล ไม่พาเข้าหน้าแรก |
| Back-end | **(—)** การยืนยันตัวตนเป็นบริการของ Supabase · ส่วน `middleware.ts` กันหน้าที่ต้องล็อกอินจากคุกกี้ก่อนโหลดหน้า |
| ฐานข้อมูล | `auth.users` (รหัสผ่านที่แฮชแล้ว ระบบไม่เก็บเอง) · อ่าน `profiles.role` และ `profiles.status` |

> `decideAccess` **ปฏิเสธทุกค่าที่ไม่ใช่ `approved` รวมถึงค่าที่หายไป** และ
> **ตรวจบทบาทก่อนสถานะ** — ถ้าให้สถานะที่อ่านไม่ได้แปลว่าผ่าน วันที่มีคนลืม
> `.select('status')` ทุกคนจะเข้าได้หมดโดยไม่มีสัญญาณใดเลย

### 2. ค้นหา/คัดกรองผู้สมัคร

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | พิมพ์คำค้นหาด้วยภาษาธรรมชาติ (ไทยหรืออังกฤษ) · แก้ชิปตัวกรองหรือแก้คำอธิบายแล้วค้นใหม่ |
| Front-end | `app/(app)/search/page.tsx` เรียกสอง endpoint ตามลำดับ · **รวม**ชิปของ AI กับชิปที่ผู้ใช้ตั้งเอง (`mergeFilters`) ไม่เขียนทับ · แยกข้อความ "ไม่พบผู้สมัคร" ออกจาก "ค้นหาไม่ได้" |
| Back-end | `POST /api/search/parse` → เรียก Gemini **ครั้งเดียว** สกัดเป็น `semanticQuery` + ชิป (ล้มเหลวได้ ถอยไปใช้คำค้นดิบ) · `POST /api/search` → แปลงข้อความเป็นเวกเตอร์ (แคชต่ออินสแตนซ์) คัดชิปทักษะที่ไม่มีคนถืออยู่ออก แล้วเรียก RPC |
| ฐานข้อมูล | `match_candidates_filtered` **กรองใน SQL ก่อนจัดอันดับ** ด้วยระยะโคไซน์ `<=>` บน `candidates.embedding` · อ่าน `education` / `candidate_skills` / `skills` ประกอบเงื่อนไข แล้วอ่านชื่อจาก `candidates` |

> **การจัดอันดับไม่ใช้ AI เลย** เป็นคณิตศาสตร์ของเวกเตอร์ล้วน · AI ถูกเรียก
> เพื่อ "สกัดตัวกรอง" เท่านั้น **เป็นเหตุผลที่ระบบอยู่ในโควตาฟรีได้แม้ผลมีหลายสิบคน**

### 3. ประเมินความเหมาะสมของผู้สมัคร

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | เปิดหน้ารายละเอียดผู้สมัคร กรอกความต้องการของตำแหน่งงาน (หรือใช้ค่าตั้งต้นจากหน้าตั้งค่า) กดประเมิน |
| Front-end | `components/AnalyzePanel.tsx` ส่งคำขอและแสดงคะแนน 0-100 พร้อมเหตุผลภาษาไทย |
| Back-end | `POST /api/analyze` → `scoreCandidateAgainst` · คำนวณค่าแฮชของข้อความความต้องการ **อ่านแคชก่อนเสมอ** ถ้าเคยประเมินแล้วคืนผลเดิมโดยไม่เรียก AI |
| ฐานข้อมูล | อ่าน `analyses` ด้วยคู่ `(candidate_id, requirement_hash)` · อ่านโปรไฟล์จาก `candidates` + `education` + `experience` + `candidate_skills` · เขียนผลใหม่ลง `analyses` |

> **อ่านแคชไม่ได้ให้บันทึกข้อผิดพลาดแล้วไปต่อ** (คำนวณใหม่ยังได้คำตอบที่ถูก
> แค่แพงกว่า) · **เขียนแคชไม่ได้ก็ไม่โยนข้อผิดพลาด** เพราะคะแนนคำนวณเสร็จแล้วจริง
> — บอกผู้ใช้ว่าล้มเหลวตอนนั้นจะผิด

### 4. จัดการ Shortlist

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | กดปุ่มบันทึกที่แถวผลการค้นหาหรือหน้าผู้สมัคร · ติ๊กเข้า/ติ๊กออกได้หลายรายการ · ตั้งชื่อรายการใหม่ · แก้ชื่อหรือลบที่หน้า `/shortlists` |
| Front-end | `components/SaveToShortlist.tsx` + `app/(app)/shortlists/page.tsx` · **ไม่เปลี่ยนเครื่องหมายติ๊กจนคำขอสำเร็จ** · กันการกดซ้ำที่ทำให้ add กับ remove วิ่งพร้อมกัน |
| Back-end | **(—)** ยิง PostgREST ตรงด้วยคีย์สาธารณะ |
| ฐานข้อมูล | `shortlists` (ชื่อยาว 1-60 ตัวอักษรบังคับที่ชั้นฐาน) · `shortlist_candidates` คีย์หลักคู่ `(shortlist_id, candidate_id)` · **RLS จำกัดให้เห็นเฉพาะของเจ้าของ** |

> **`shortlist_candidates` ไม่มีคอลัมน์บันทึกย่อ** (ลบเมื่อ migration 022a)
> อย่าเขียนขั้นตอน "กรอกหมายเหตุ" ลงในเล่ม

### 5. ดูข้อมูลผ่านแดชบอร์ด

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | เปิดหน้าแรกหลังล็อกอิน ดูการ์ดสถิติ กราฟทักษะที่พบบ่อย กราฟแหล่งที่มาของข้อมูล และ Shortlist ของตน |
| Front-end | `app/(app)/dashboard/page.tsx` เป็น **Server Component** เรนเดอร์จากข้อมูลที่อ่านมาแล้ว ไม่มีการเรียก API จากเบราว์เซอร์ · แท่งกราฟเป็น `<div>` กำหนดความกว้างเป็นเปอร์เซ็นต์ **ไม่ใช้ไลบรารีกราฟ** |
| Back-end | โค้ดฝั่งเซิร์ฟเวอร์ของหน้าเดียวกัน (`lib/dashboard/stats.ts`) ใช้สิทธิ์ service-role · **คืนสถานะล้มเหลวมาด้วย ไม่กลืนข้อผิดพลาดเป็นรายการว่าง** |
| ฐานข้อมูล | นับด้วย SQL ผ่าน `top_skills` และ `candidate_source_counts` **ไม่ดึงทั้งตารางมานับใน JavaScript** · อ่าน `candidates` / `jobs` / `shortlists` |

> "ยังไม่มีข้อมูล" เป็นคำตอบที่ผู้ใช้เชื่อทันทีโดยไม่สงสัย **จึงห้ามเอามาใช้ตอนระบบพัง**

### 6. ตั้งค่าข้อมูลส่วนตัว

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | แก้ชื่อที่แสดง · ตั้งข้อความความต้องการที่ใช้บ่อย · เปลี่ยนรหัสผ่าน · ลบข้อมูลประเมินตัวเองของตน |
| Front-end | `app/(app)/settings/page.tsx` + `DisplayNameCard` + `ChangePasswordCard` · **ปิดปุ่มบันทึกเมื่ออ่านค่าเดิมไม่สำเร็จ** เพื่อไม่ให้ผู้ใช้กดทับค่าจริงด้วยช่องว่าง |
| Back-end | **(—)** สำหรับชื่อและการตั้งค่า · การเปลี่ยนรหัสผ่านผ่านบริการยืนยันตัวตนของ Supabase ซึ่ง**ตรวจรหัสผ่านเดิมด้วยการลองเข้าสู่ระบบก่อน** |
| ฐานข้อมูล | `profiles` — ได้สิทธิ์เขียนเฉพาะ `display_name` และ `settings` เท่านั้น (column-level grant, migration 019) · `display_name` ยาวได้ 1-254 ที่ชั้นฐาน · การตั้งค่าเป็น jsonb ที่**รวมค่าเดิม ไม่เขียนทับทั้งก้อน** |

> **คอลัมน์ `role` และ `status` ไม่อยู่ในสิทธิ์เขียนโดยตั้งใจ** — ถ้าอยู่
> ผู้ใช้จะยิงคำขอตรงด้วยคีย์สาธารณะแล้วตั้งตัวเองเป็นผู้ดูแลระบบหรืออนุมัติตัวเองได้ทันที

### 7. ประเมินโปรไฟล์ของตนเอง

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | อัปโหลดไฟล์เรซูเม่ PDF **หรือ** เลือกกรอกข้อมูลเอง · **ตรวจและแก้ร่างข้อมูลก่อนกดบันทึก** · ดูจุดแข็ง จุดที่ยังขาด และตำแหน่งงานที่เหมาะ |
| Front-end | `SelfAssessmentStart` (ทางเข้าสองทางที่เห็นได้ทั้งคู่) → `ProfileForm` ให้ตรวจร่าง · ส่งไฟล์เป็น `FormData` ไม่ใช่ base64 |
| Back-end | `POST /api/self-assessment/parse` อ่าน PDF ด้วย Gemini แบบ multimodal **แล้วคืนร่าง ไม่เขียนอะไรเลย** · `POST /api/self-assessment` รับร่างที่ผู้ใช้ยืนยันแล้ว → ประเมิน + สร้างเวกเตอร์ + บันทึกในคำขอเดียว · `POST .../[id]/score` จัดอันดับงาน |
| ฐานข้อมูล | `self_profiles` **แยกจาก `candidates` โดยสิ้นเชิง** · `resume_assessments` เก็บคะแนนงานตาม `requirement_hash` · จัดอันดับด้วย `match_jobs` บน `jobs.embedding` |

> **ความเป็นส่วนตัวอยู่ในโครงสร้าง ไม่ใช่ในเงื่อนไข** — ตารางแยกกัน ข้อมูลที่ผู้ใช้
> อัปโหลดเองจึงไม่มีทางไปโผล่ในการค้นหาของฝ่ายบุคคล · ทุก route ใช้ service-role
> ซึ่งข้าม RLS **การกรองด้วยเจ้าของในโค้ดจึงเป็นตัวควบคุมการเข้าถึง ไม่ใช่ชั้นที่สอง**
> · route ที่รับ id ตอบ **404 ไม่ใช่ 403** ให้คนที่ไม่ใช่เจ้าของ เพื่อไม่ยืนยันว่า id นั้นมีอยู่
>
> **การจัดอันดับงานไม่เรียก AI เลยสักครั้ง**

### 8. นำเข้าข้อมูลผู้สมัคร

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | *(data_manager ขึ้นไป)* วางไฟล์ CSV ที่หน้า `/import/manual` · หรือใช้ `/import/xray` สร้างคำค้น Google แล้วกรอกตามเทมเพลต · ดูสถานะการดึงอัตโนมัติที่ `/import/auto` |
| Front-end | `components/ImportForm.tsx` (ใช้ทั้งสองหน้าโดยตั้งใจ เพราะ X-ray เป็นงานสามขั้นในรอบเดียว) · `CsvTemplateButton` ให้ดาวน์โหลดเทมเพลตที่พิสูจน์กับตัวอ่านไฟล์จริงแล้ว |
| Back-end | `POST /api/ingest` → แปลงไฟล์ (รับชื่อคอลัมน์ได้สองชุด) → `upsertCandidate` ทีละแถว · **ตรวจรายชื่อระงับก่อนสร้างเวกเตอร์** · เทียบค่าแฮชข้อความก่อนเรียก Gemini จึงข้ามแถวที่ไม่เปลี่ยน |
| ฐานข้อมูล | `candidates` + `education` + `experience` + `skills` / `candidate_skills` · ตัดข้อมูลซ้ำด้วย `linkedin_url` (unique index บางส่วน) แล้วถอยไปใช้ชื่อ · บันทึกการกระทำลง `activity_log` |

> **การดึงอัตโนมัติยังเปิดใช้งานไม่ได้** สคริปต์และ workflow มีอยู่จริงแต่ไม่มี
> บัญชีบริการภายนอก ตาราง `ingest_runs` จึง**ยังไม่มีแถวใดเลย** — เส้นทางที่ใช้งาน
> ได้จริงคือการวางไฟล์ด้วยมือเท่านั้น (ดูข้อ 20 ของ `2026-10-20-revision-review.md`)

### 9. ระงับข้อมูลตามคำขอของเจ้าของข้อมูล

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | *(data_manager ขึ้นไป)* กดระงับที่หน้าผู้สมัคร · ดูรายชื่อที่ระงับแล้วที่ `/import/suppressed` |
| Front-end | `components/SuppressButton.tsx` + `SuppressedList` |
| Back-end | `POST /api/candidates/[id]/suppress` — **บันทึกรายชื่อระงับก่อน แล้วจึงลบ** เป็นลำดับที่สลับไม่ได้ |
| ฐานข้อมูล | เขียน `suppressed_profiles` → ลบแถวใน `candidates` (ลูกถูกลบตาม cascade) → บันทึก `activity_log` |

> **ลบก่อนแล้วบันทึกล้มเหลวจะได้สถานะที่แย่ที่สุด** คือข้อมูลหายแต่รอบนำเข้าถัดไป
> ดึงกลับมาใหม่ · การตรวจรายชื่อระงับอยู่ใน `upsertCandidate` **ไม่ใช่ในสคริปต์**
> ทุกเส้นทางนำเข้าจึงผ่านด่านนี้เหมือนกันหมด

### 10. ตรวจสอบคิวข้อมูลนำเข้า

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | *(data_manager ขึ้นไป)* ดูคิวที่ `/import/pending` อนุมัติทีละคนหรือปฏิเสธเป็นกลุ่ม |
| Front-end | `components/PendingReviewTable.tsx` |
| Back-end | `POST /api/pending/[id]/approve` · `POST /api/pending/reject` |
| ฐานข้อมูล | อ่าน/ลบ `pending_candidates` · การอนุมัติย้ายข้อมูลเข้า `candidates` |

> ⚠ **ยังเปิดใช้งานไม่ได้ในเวอร์ชันนี้** คิวเติมได้จากสคริปต์ดึงอัตโนมัติทางเดียว
> ซึ่งปิดอยู่ **การนำเข้าด้วยมือไม่ผ่านตัวคัดกรองเลย** ทุกแถวเข้าตารางผู้สมัครโดยตรง
> (UAT DM-10 · DM-11) · **ต้องกำกับข้อนี้ในคำบรรยายใต้ภาพ ไม่ใช่ในกล่อง**

### 11. จัดการตำแหน่งงาน

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | *(data_manager ขึ้นไป)* สร้าง แก้ไข ลบตำแหน่งงาน · ดูผู้สมัครที่เหมาะกับงานนั้นเรียงตามลำดับ |
| Front-end | `components/JobForm.tsx` · `JobMatches` · `DeleteJobButton` · **`member` มองไม่เห็นฟอร์มเลย** และข้อความตอนไม่มีงานต่างกันตามสิทธิ์ |
| Back-end | `POST` / `PATCH` / `DELETE /api/jobs` กั้นที่ `data_manager` ทั้งสามคำสั่ง · ตรวจความยาวข้อความและห้ามทศนิยมในจำนวนปีก่อนถึงฐาน · `PATCH` **ตัดฟิลด์แหล่งที่มาทิ้งที่ชั้น route** · สร้างเวกเตอร์ใหม่เมื่อข้อความที่ใช้ฝังเปลี่ยน |
| ฐานข้อมูล | `jobs` (+ `jobs.embedding`) · **ลบแคชคะแนนใน `analyses` เมื่อข้อความความต้องการเปลี่ยน** เพราะแคชคีย์ด้วยค่าแฮชของข้อความ · จัดอันดับผู้สมัครด้วย `match_candidates` |

> **ซ่อนฟอร์มจาก `member` ไม่ใช่การเพิ่มด่าน** ด่านจริงอยู่ที่ route —
> แต่การให้คนกรอกฟอร์มจนครบแล้วถูกปฏิเสธคือการบอกให้ทำสิ่งที่ทำไม่ได้
> **ซึ่งแย่กว่าไม่บอกอะไรเลย**

### 12. จัดการข้อมูลผู้ใช้

| ชั้น | ทำอะไร |
|---|---|
| ผู้ใช้ | *(admin เท่านั้น)* ดูคิวบัญชีที่รออนุมัติ · อนุมัติหรือถอนสิทธิ์ · เปลี่ยนบทบาท |
| Front-end | `app/(app)/admin/users/page.tsx` (Server Component) + `AccountStatusActions` + `RoleSelect` · **ย้อนค่าในช่องเมื่อคำขอล้มเหลว** และใช้สีแดงกับข้อความผิดพลาด |
| Back-end | `POST /api/admin/users` (เปลี่ยนบทบาท) · `POST /api/admin/users/[id]/status` (อนุมัติ/ปฏิเสธ) · ใช้สิทธิ์ service-role · **ห้ามผู้ดูแลระบบเปลี่ยนบทบาทหรือสถานะของตัวเอง** · ไม่ส่งข้อความดิบจากฐานข้อมูลออกไป |
| ฐานข้อมูล | เขียน `profiles.role` และ `profiles.status` **ซึ่งเป็นสองคอลัมน์ที่เบราว์เซอร์เขียนไม่ได้** · บันทึก `activity_log` ทั้งสองการกระทำ |

> **ข้อจำกัดที่ต้องเขียนไว้ตรงๆ** กฎห้ามแก้ตัวเองกันกรณีที่เกิดจริงได้
> แต่**ไม่รับประกันว่าจะมีผู้ดูแลระบบเหลือเสมอ** — ผู้ดูแลสองคนที่ลดสิทธิ์ของ
> อีกฝ่ายพร้อมกันจะผ่านทั้งคู่ · กู้ได้ทางเดียวคือแก้ที่ฐานข้อมูลโดยตรง

## ส่วนที่ 3 — ข้อค้นพบที่ตารางนี้ทำให้เห็น (เขียนลงเล่มได้)

**สาม Use case จากสิบสองไม่มีโค้ด Back-end ของเราในเส้นทางเลย** — ข้อ **1**
(เข้าสู่ระบบ) · ข้อ **4** (จัดการ Shortlist) · ข้อ **6** (ตั้งค่าข้อมูลส่วนตัว
เฉพาะส่วนชื่อและการตั้งค่า ส่วนการเปลี่ยนรหัสผ่านผ่านบริการยืนยันตัวตน)
ทั้งสามคุยกับฐานข้อมูลตรงผ่าน REST API ที่ Supabase สร้างให้อัตโนมัติ
ด้วยคีย์สาธารณะที่ฝังอยู่ในหน้าเว็บ

**ข้อ 5 (แดชบอร์ด) ไม่นับรวม** แม้เบราว์เซอร์จะไม่เรียก API เลย เพราะโค้ดที่
อ่านฐานข้อมูลเป็นโค้ดฝั่งเซิร์ฟเวอร์ของเราที่รันตอนเรนเดอร์หน้า และใช้สิทธิ์
service-role — **คนละเส้นทางกับสามข้อข้างบนโดยสิ้นเชิง**

**คีย์นั้นเป็นความลับไม่ได้** เพราะ Next.js ฝังค่าลงไฟล์ที่ส่งไปเบราว์เซอร์ตอน build
**ด่านจริงจึงเป็นกลไกที่ชั้นฐานข้อมูลสองชั้นที่ทำงานต่างกัน**

| ชั้น | กรองอะไร | ตัวอย่างในระบบ |
|---|---|---|
| Row Level Security | **กรองแถว** | ผู้ใช้เห็น Shortlist ที่ `owner_id` เป็นตนเองเท่านั้น |
| Column-level GRANT | **กรองคอลัมน์** | เขียน `profiles` ได้เฉพาะ `display_name` กับ `settings` · อ่าน `candidates` ด้วยคีย์สาธารณะได้เพียงสามคอลัมน์ |

**ต้องมีทั้งคู่** — RLS อย่างเดียวกันการแก้แถวคนอื่นได้ แต่ไม่กันการแก้คอลัมน์
`role` **ในแถวของตัวเอง** ซึ่งเท่ากับยกสิทธิ์ผู้ดูแลระบบให้ใครก็ได้ที่ล็อกอิน

> **จุดนี้คือคำตอบที่ดีสำหรับคำถาม "ความปลอดภัยอยู่ที่ไหน"** เพราะคำตอบว่า
> "ตรวจที่หน้าจอ" ใช้ไม่ได้ — หน้าจอไม่ใช่ด่าน ใครก็ยิงคำขอตรงได้
> **และสิ่งที่ตรงข้ามกันคือ Use case ที่ผ่าน Back-end จะใช้สิทธิ์ service-role
> ซึ่งข้าม RLS ทั้งหมด** การกรองด้วยเจ้าของในโค้ดจึงเป็นตัวควบคุมการเข้าถึงเอง
> ไม่ใช่ชั้นเสริม — **สองเส้นทางนี้ต้องไม่เอารูปแบบของกันและกันไปใช้สลับกัน**
