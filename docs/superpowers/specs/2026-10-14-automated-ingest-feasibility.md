# การดึงข้อมูลผู้สมัครอัตโนมัติ — ผลการตรวจสอบและข้อจำกัด

**วันที่ตรวจ:** 2026-10-14
**สถานะ:** ไม่มีทางเลือกใดผ่านเกณฑ์ · ท่อรับข้อมูลในเฟส 8 ยังไม่มีแหล่งข้อมูลที่ต่อได้
**เอกสารนี้ไม่ใช่สเปคสำหรับสร้าง** เป็นบันทึกผลการตรวจ เพื่อไม่ให้มีใครเสียเวลาซ้ำ
และเพื่อยกไปเขียนเป็นหัวข้อข้อจำกัดของงานในปริญญานิพนธ์ได้โดยตรง

## คำถามที่ตั้งต้น

ท่อรับข้อมูลอัตโนมัติสร้างเสร็จตั้งแต่เฟส 8 — `scripts/sync-phantombuster.ts`,
`ingest_runs`, `pending_candidates`, `suppressed_profiles`, `classifyRow`,
GitHub Actions ที่ปิด `schedule:` ไว้ **ขาดแค่แหล่งข้อมูลที่ต่อได้จริง**

เงื่อนไขที่ต้องการ

- ฐานข้อมูล**โตขึ้น** ด้วยคนใหม่ ไม่ใช่แค่อัปเดตคนเดิม
- ทำงานเองตามเวลา (รายเดือน)
- **งบประมาณศูนย์บาท**
- ประตูเข้าฐานข้อมูลคือ **คนไทยที่จบจากต่างประเทศ** ส่วนสายอาชีพ ประสบการณ์
  ทักษะ เป็นตัวกรองที่ผู้ใช้เลือกเองตอนค้นหา ไม่ใช่เงื่อนไขตอนนำเข้า

## 1. Bright Data — วัดด้วยการรันจริง ไม่ใช่อ่านเอกสาร

ใช้เครดิตไป **23 จาก 5,000** เพื่อตรวจสองอย่างนี้

### 1.1 เครดิตฟรีอยู่คนละผลิตภัณฑ์กับตัวที่ค้นหาด้วยเงื่อนไขได้

หน้าราคาติดป้าย FREE TIER ไว้ที่ Unlocker API · SERP API · **Scraper API** ·
Scraper Studio — ส่วน **Datasets เขียนว่า "Starts from $250/100K rec" ไม่มี free tier**

เครดิตฟรี 5,000 คือ Scraper API · **Datasets Marketplace คือตัวเดียวที่กรอง
ด้วยเงื่อนไข (ภูมิศาสตร์ หมวด ช่วงเวลา) ก่อนซื้อได้** 543 ล้านเรคคอร์ด รีเฟรชรายเดือน
ส่งเข้า S3/Webhook/API ได้ — ตรงกับท่อที่มีอยู่พอดี แต่เกินงบ

### 1.2 `collect by URL` — ข้อมูลครบที่สุดของ Bright Data และยังไม่พอ

snapshot `sd_mv7sv0ey6vlyfwnv5` · 5 เรคคอร์ด · **success rate 100%** · 1 นาที 11 วินาที
· อัตรา $1.50/1k records · ป้อน URL ของผู้สมัครที่อยู่ในฐานข้อมูลอยู่แล้ว
เพื่อให้เทียบกับคำตอบที่รู้อยู่แล้วได้

```
#   education  experience  position  about   country_code
0     ไม่มี       ไม่มี       ไม่มี     มี         TH
1      มี        ไม่มี       ไม่มี     มี         TH
2     ไม่มี       ไม่มี       ไม่มี    ไม่มี        TH
3      มี        ไม่มี       ไม่มี     มี         TH
4      มี        ไม่มี       ไม่มี    ไม่มี        TH
```

**`experience: null` และ `position: null` ทุกเรคคอร์ด ทั้งที่รายงาน success rate 100%**
และ **ไม่มีฟิลด์ `skills` อยู่ใน output เลย** (34 ฟิลด์ ไม่มีสักตัว)

**ปัญหาที่อันตรายกว่าการไม่มีข้อมูล — การมีข้อมูลที่ไม่ครบแต่ดูเหมือนครบ**

แต่ละคนที่มี `education` จะมีหลายรายการ **แต่มีเฉพาะรายการแรกที่มีชื่อสถาบัน**
ที่เหลือมีแต่ `start_year` / `end_year`

```
rec1: 3 รายการ → ชื่อ 1 (มหาวิทยาลัยในไทย) · อีก 2 รายการมีแต่ปี 2014-2016, 2008-2011
rec3: 4 รายการ → ชื่อ 1 (UST, Korea)       · อีก 3 รายการมีแต่ปี
rec4: 3 รายการ → ชื่อ 1 (University of Hull) · อีก 2 รายการมีแต่ปี
```

โครงสร้างของแต่ละรายการ:
`description · description_html · end_year · institute_logo_url · start_year · title · url`
— **`title` กับ `url` โผล่เฉพาะรายการแรก** และ**ไม่มีฟิลด์ `degree` เลย**

**ทำไมเรื่องนี้เป็นพิษกับโปรเจกต์นี้โดยเฉพาะ** — rec1 มีชื่อสถาบันเดียวคือมหาวิทยาลัยไทย
ระบบจะตัดสินว่า "ไม่ได้จบต่างประเทศ" แล้วปฏิเสธ **แต่เขามีการศึกษาอีกสองรายการ
ที่ไม่มีชื่อ ซึ่งอาจเป็นปริญญาจากต่างประเทศก็ได้ และไม่มีทางรู้**

ข้อมูลที่หายแบบนี้ไม่ทำให้ระบบ error มันทำให้ระบบ**ตอบผิดอย่างมั่นใจ** ซึ่งเป็น
ความล้มเหลวชนิดเดียวกับที่ `CLAUDE.md` บันทึกไว้หลายครั้ง — "ไม่พบผลลัพธ์" ตอนระบบ
ค้นหาพัง · `width: NaN%` ที่กลายเป็นแท่งเต็ม · 404 ตอนฐานข้อมูลล่ม

### 1.3 `people search` — ค้นหาด้วย "ชื่อคน" ไม่ใช่ "เงื่อนไข"

snapshot `sd_mudxwe3e1jpzldapbw` · 18 เรคคอร์ด

```
input ที่มันรับ: first_name · last_name · url
```

ไม่มีตำแหน่งงาน ไม่มีสถาบัน ไม่มีทักษะ ไม่มีประเทศ — **ต้องรู้อยู่แล้วว่าจะหาใคร**

output มี **9 ฟิลด์** เทียบกับ 34 ของ collect-by-URL และเป็น**ตัวอย่างจากหน้าผลค้นหา
ไม่ใช่ข้อมูลโปรไฟล์** — `education` กับ `experience` เป็น**สตริงที่ถูกตัด**

```
[0] Thailand       education='Asian Institute of Technology'
[2] Stanford, CA   experience='Stanford University School of Medicine, +4 more'
[4] Brestski Rayon experience='Маркформель, +4 more'
[5] Leeds          experience='Elizabeth School of London'
[10] education=', +2 more'      ← ชื่อสถาบันว่างเปล่า
[11] education=', +1 more'      ← ชื่อสถาบันว่างเปล่า
```

`education` มีค่า 4/18 · `experience` มีค่า 11/18 · ไม่มีวันที่ ไม่มีตำแหน่ง
ไม่มี `about` ไม่มี `country_code`

**และผลลัพธ์ไม่ตรงเป้า** — ค้นชื่อคนไทยหนึ่งชื่อ ได้ 18 คนกระจายอยู่ที่ Stanford ·
ฝรั่งเศส · เบลารุส · ลีดส์ · อินโดนีเซีย มันจับคู่ชื่อแบบหลวมทั่วโลก ไม่ได้กรองอะไร

## 2. joeyism/linkedin_scraper — ตรวจจากโค้ดจริง

4.5k ดาว · 108 issue ค้าง · 38 PR ค้าง · v3.0 เขียนใหม่ด้วย Playwright + async + Pydantic

### 2.1 ต้องล็อกอินด้วยบัญชี LinkedIn จริง

```python
await browser.load_session("session.json")
```

ไม่มีทางเลี่ยง · โค้ดมี `RateLimitError` · `AuthenticationError` ·
`ProfileNotFoundError` เป็นคลาสของตัวเอง แปลว่าผู้เขียนรู้ว่าเจอบ่อย

**บัญชีที่ใช้คือบัญชีที่เสี่ยงถูกจำกัดหรือปิด**

### 2.2 หาคนใหม่ไม่ได้

มี `PersonScraper` · `CompanyScraper` · `JobSearchScraper` · `CompanyPostsScraper`
— **ไม่มีตัวค้นหาคน** · `scraper.scrape(url)` รับ URL ที่มีอยู่แล้วเท่านั้น

### 2.3 README ไม่ตรงกับโค้ด

README โฆษณาว่า `Person` มี `headline` และ `skills` · **โค้ดจริงไม่มีทั้งคู่**

```python
class Person(BaseModel):
    linkedin_url · name · location · about · open_to_work
    experiences · educations · interests · accomplishments · contacts
```

### 2.4 แต่มันให้วันที่ ซึ่งเป็นสิ่งที่ X-ray ให้ไม่ได้

```python
class Experience(BaseModel):
    position_title · institution_name · linkedin_url
    from_date · to_date · duration · location · description

class Education(BaseModel):
    institution_name · degree · linkedin_url
    from_date · to_date · description
```

`from_date`/`to_date` คือสิ่งที่ทำให้ `parseLinkedInDateRange` และ
`computeYearsExperience` ทำงานได้ · **joeyism ให้มากกว่า Bright Data ในฟิลด์
ที่สำคัญที่สุด** เพราะมันอ่านหน้าโปรไฟล์ในฐานะคนที่ล็อกอินอยู่ — ซึ่งเป็นทั้ง
เหตุผลที่มันได้ผลและเหตุผลที่มันเสี่ยง

### 2.5 License ประกาศขัดกันเอง

badge ใน README เขียน **Apache-2.0** · แถบข้างของ repo เขียน **GPL-3.0**
ซึ่งเป็น copyleft · ความไม่ชัดเจนนี้เป็นปัญหาสำหรับงานที่ต้องส่งมอบ

## 3. joeyism เทียบ PhantomBuster

**สิ่งที่คนคิดว่าต่างแต่ไม่ต่างคือความเสี่ยง** — PhantomBuster ต้องการ cookie
`li_at` ส่วน joeyism ต้องการ `session.json` **คือสิ่งเดียวกันคนละชื่อ**
และผิดข้อกำหนดการใช้งานของ LinkedIn เท่ากัน

| | PhantomBuster | joeyism |
|---|---|---|
| browser รันที่ไหน | คลาวด์ของเขา IP datacenter | เครื่องผู้ใช้ IP บ้าน |
| cookie อยู่ที่ไหน | **อัปโหลดให้บริษัทต่างประเทศ** | อยู่ในเครื่อง |
| ค้นหาคนใหม่ | **ได้** มี Search Export phantom | ไม่ได้ |
| ฟิลด์ | skills · industry · fieldOfStudy · professionalEmail · ช่วงวันที่ | ช่วงวันที่ · description · location · **ไม่มี skills ไม่มี headline** |
| ดูแลตอน LinkedIn เปลี่ยนหน้า | เขา (คือสิ่งที่จ่ายเงินซื้อ) | **ผู้ใช้เอง** |
| ราคา | เสียเงิน | ฟรี |
| ต่อกับท่อที่มีอยู่ | **ต่อได้เลย** `parseLinkedInCsv` + `KNOWN_COLUMNS` เขียนมาเพื่อมัน | ต้องเขียน adapter ใหม่ |

**ข้อได้เปรียบเรื่องการค้นหาของ PhantomBuster พังในทางปฏิบัติ** — `CLAUDE.md`
บันทึกไว้แล้วว่าการค้นใน LinkedIn ด้วยบัญชีใหม่คืน "LinkedIn Member" ทั้งหน้า
ไม่มีชื่อ ไม่มี URL · และบัญชีทิ้งที่สร้างมาเพื่องานนี้คือบัญชีที่ LinkedIn ไว้ใจน้อยที่สุด

**ข้อที่ควรชั่งที่สุดสำหรับเล่ม คือเรื่อง cookie** — PhantomBuster แปลว่าส่งกุญแจบัญชี
ให้บริษัทต่างประเทศถือไว้ ซึ่งในเล่มที่มีบทเรื่อง PDPA และการโอนข้อมูลข้ามพรมแดน
**อธิบายยากกว่าเรื่อง ToS เสียอีก**

## 4. ผลกระทบกับโค้ดที่มีอยู่ ถ้าฝืนใช้ข้อมูลที่ไม่ครบ

### `classifyRow` — ทุกแถวตกเกณฑ์

ใช้สี่เกณฑ์: `headline` · `experience` · `linkedin_url` · `education`

ข้อมูลจาก Bright Data มี `position` ว่าง 5/5 และ `experience` ว่าง 5/5
→ **ทั้งหมดเข้า `pending_candidates` ให้กดอนุมัติทีละคน** ซึ่งลบความหมาย
ของคำว่าอัตโนมัติทิ้งทั้งหมด

**`headline` แก้ที่ฝั่งเราได้** — joeyism ให้ `position_title` กับ `institution_name`
ของงานล่าสุด ประกอบเป็น headline ได้โดยไม่ต้องพึ่งแหล่งข้อมูล (ยังไม่ได้ทำ)

### `buildEmbedText` — เวกเตอร์บางกว่าที่เคยวัดว่าแย่ที่สุด

ใช้ `headline` · `industry` · `summary` · `skills` · education · experience

จาก Bright Data จะเหลือแค่ `about` กับชื่อสถาบันหนึ่งชื่อ — **บางกว่ากรณีที่
`scripts/ablate-embedding.ts` วัดไว้ว่าแย่ที่สุด** (Spearman 0.856 ตอนตัด
skills + summary) เพราะรอบนี้ตัด headline กับ experience ไปด้วย

### `computeYearsExperience` — เป็น 0 ทุกคน

ไม่มี `experience` แปลว่าไม่มีช่วงเวลา → `parseLinkedInDateRange` คืน null →
**คนกลุ่มนี้หลุดตัวกรอง "ประสบการณ์ขั้นต่ำ" ทุกครั้งโดยไม่มีอะไรบอก**
อาการเดียวกับที่ X-ray search เจอและบันทึกไว้แล้ว

## 5. ของที่ได้มาและเก็บไว้ใช้ได้ ไม่ว่าจะเลือกทางไหน

**`url` ของสถาบันจาก LinkedIn บอกประเทศมาในตัว**

```
https://th.linkedin.com/school/...   → ไทย
https://kr.linkedin.com/school/...   → เกาหลี
https://uk.linkedin.com/school/...   → สหราชอาณาจักร
```

ซับโดเมนคือรหัสประเทศ **ใช้ตัดสิน "จบจากต่างประเทศ" ได้ตรงๆ โดยไม่ต้องเดาจาก
ชื่อสถาบัน** ซึ่งแก้ปัญหาที่ `lib/self/taxonomy.ts` เตือนไว้เรื่องชื่อปนไทย-อังกฤษ
· ใช้ได้กับทุกแหล่งที่คืน URL ของหน้า school มาด้วย

## 6. ทางที่สะอาดที่สุดคือทางที่สร้างไว้แล้วและยังไม่ได้ใช้เป็นช่องทางเติบโต

`/self-assessment` รับเรซูเม่ PDF ที่**เจ้าของข้อมูลอัปโหลดเอง** แล้ว `parsePdf`
สกัด education กับ experience ครบพร้อมวันที่ — **ข้อมูลสมบูรณ์กว่าทุกแหล่งที่ตรวจมา
ทั้งหมด** เพราะมันคือ CV ที่เจ้าตัวเขียนเอง

- ไม่มีค่าใช้จ่าย
- ไม่มีบัญชีให้เสี่ยง ไม่มี ToS ให้ผิด
- **PDPA มาตรา 25 หายไปทั้งข้อ** เพราะไม่ใช่การเก็บจากแหล่งอื่น เจ้าของข้อมูลให้เอง
  — ซึ่งเป็นหน้าที่ที่ `CLAUDE.md` บันทึกไว้ว่าหน้าเว็บ `/privacy` แก้ให้ไม่ได้

**ติดอยู่อย่างเดียวที่เป็นการออกแบบไว้ตั้งใจ** — `self_profiles` แยกจาก `candidates`
เพื่อไม่ให้ข้อมูลที่อัปโหลดไหลไปหาการค้นหาของผู้สรรหา · ถ้าจะใช้ทางนี้
**ต้องขอความยินยอมตอนอัปโหลดอย่างชัดเจน** ซึ่งเป็นงานออกแบบและงานกฎหมาย
ไม่ใช่งานเทคนิค · ข้อเสียคือมันไม่ทำให้ฐานโตเร็วแบบการ scrape

## 7. ข้อผิดพลาดของการตรวจรอบนี้ ที่ต้องบันทึกไว้

**ตั้งเกณฑ์ผ่าน/ไม่ผ่านโดยไม่ครอบฟิลด์ที่สำคัญที่สุด** — ตอนออกแบบการทดสอบ
เอา `education` เป็นตัวตัดสินแล้ว**ไม่ได้ใส่ `experience` เข้าไปในเกณฑ์เลย**
เพราะเอกสารของผู้ให้บริการลิสต์ไว้ว่ามี จึงถือว่ามันต้องมา · ผลคือข้อที่ทำให้ตกจริง
เป็นข้อที่ไม่ได้ตั้งเกณฑ์ไว้

> **เอกสารของผู้ให้บริการไม่ใช่หลักฐาน** หลักฐานคือ output จากการรันจริง
> และต้องตั้งเกณฑ์ให้ครอบทุกฟิลด์ที่โค้ดเราใช้ ไม่ใช่เฉพาะฟิลด์ที่สงสัย

**อ้างตัวเลขที่ยืนยันไม่ได้** — เคยอ้างว่า "Experience/Education เหลือความครบราว 2%
หลัง 13 พ.ย. 2025" แล้วหาแหล่งยืนยันปัจจุบันไม่เจอ · ทิศทางบังเอิญถูก (วัดได้
`experience` 0/5) แต่**ตัวเลขที่ยืนยันไม่ได้ไม่ควรถูกใช้ตัดสินใจ**

**เข้าใจผิดจากชื่อเมนู** — เห็น "LinkedIn people search" ในแถบซ้ายแล้วสรุปว่า
ข้อสรุปเดิมเรื่องค้นหาด้วยเงื่อนไขอาจผิด · พอรันจริงพบว่าเอกสารถูกตั้งแต่แรก
มันค้นด้วยชื่อคน **ชื่อเมนูไม่ใช่สเปค**

## 8. สำหรับเขียนลงเล่ม — ข้อจำกัดของระบบ

ข้อความต่อไปนี้ยกไปใช้ได้โดยตรง

> ระบบออกแบบและพัฒนาท่อรับข้อมูลอัตโนมัติไว้ครบถ้วน ประกอบด้วยการบันทึกที่มา
> (`ingest_runs`) คิวตรวจสอบก่อนนำเข้า (`pending_candidates`) รายชื่อระงับตามคำขอ
> (`suppressed_profiles`) และการข้ามเรคคอร์ดที่ไม่เปลี่ยนแปลงด้วย `embed_hash`
> แต่**ไม่สามารถเปิดใช้งานได้จริงเนื่องจากข้อจำกัดของแหล่งข้อมูลต้นทาง** ไม่ใช่
> ข้อจำกัดของระบบเอง
>
> จากการทดสอบกับผู้ให้บริการข้อมูลเมื่อ 14 ตุลาคม 2569 พบว่า บริการที่ให้ใช้ฟรี
> คืนค่าฟิลด์ประสบการณ์ทำงานเป็นค่าว่างทุกเรคคอร์ด และคืนชื่อสถาบันการศึกษา
> เฉพาะรายการแรกเท่านั้น ทำให้ไม่สามารถตัดสินได้ว่าผู้สมัครสำเร็จการศึกษาจาก
> ต่างประเทศหรือไม่ ซึ่งเป็นเงื่อนไขหลักของระบบ · ส่วนบริการที่มีข้อมูลครบถ้วน
> มีค่าใช้จ่ายขั้นต่ำเกินขอบเขตของงาน และเครื่องมือโอเพนซอร์สที่ให้ข้อมูลครบ
> จำเป็นต้องเข้าถึงด้วยบัญชีผู้ใช้ที่ลงชื่อเข้าใช้แล้ว ซึ่งขัดกับข้อกำหนด
> การใช้งานของแพลตฟอร์มต้นทาง
>
> นอกจากนี้ ช่องทางการค้นหาผ่าน API ของเครื่องมือค้นหาถูกปิดทั้งสองราย —
> Google Custom Search JSON API ปิดรับลูกค้าใหม่และกำหนดยุติบริการ 1 มกราคม 2570
> และ Bing Search API ถูกยกเลิกถาวรเมื่อ 11 สิงหาคม 2568
>
> **ข้อจำกัดนี้สะท้อนสภาพของระบบนิเวศข้อมูลสาธารณะที่เปลี่ยนแปลงระหว่างการพัฒนา**
> มิได้เกิดจากการออกแบบระบบ และระบบยังคงรองรับการนำเข้าข้อมูลด้วยไฟล์ CSV
> และการประเมินตนเองโดยเจ้าของข้อมูลได้ตามปกติ
