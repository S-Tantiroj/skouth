## ที่มา

สามเรื่องที่ไม่เกี่ยวกันบนหน้าจอ แต่แก้พร้อมกันเพราะทั้งหมดเป็นเรื่อง
**ใครเห็นอะไรและทำอะไรได้**

1. **การลงทะเบียนเปิดให้ใครก็ได้** ทุกคนที่สมัครได้สิทธิ์ `member` ทันทีและใช้ระบบได้เลย
   — ระบบที่เก็บข้อมูลบุคคลจริงไม่ควรเปิดประตูแบบนั้น
2. **Shortlist ใช้ยาก** เพิ่มได้อย่างเดียว ไม่รู้ว่าคนนี้อยู่ในรายการไหนบ้าง
   ตั้งชื่อผิดแล้วแก้ไม่ได้ และลบรายการทิ้งไม่ได้
3. **หน้า Jobs แสดงฟอร์มที่ API ปฏิเสธ** `member` กรอกฟอร์มสร้างงานจนเสร็จแล้วถูกปฏิเสธ
   เพราะ `POST /api/jobs` กั้น `data_manager` ไว้ตั้งแต่ Phase 9 แต่หน้าจอไม่เคยถูกแก้ตาม

## ขอบเขต

**ทำ**

- สถานะบัญชี `pending` / `approved` / `rejected` พร้อมหน้าจอให้ผู้ดูแลอนุมัติและปฏิเสธ
- `SaveToShortlist` แบบติ๊กเพิ่ม-ติ๊กออก ใช้ได้ที่หน้ารายละเอียดผู้สมัคร ผลการค้นหา
  และรายชื่อผู้สมัครในหน้างาน
- หน้า `/shortlists` แก้ชื่อและลบรายการได้
- ซ่อนการ์ดสร้างงานจากผู้ใช้ที่ไม่มีสิทธิ์

**ไม่ทำ**

- ไม่มีโน้ตต่อผู้สมัครใน Shortlist — **ลบคอลัมน์ `note` ทิ้ง**
- **ไม่ส่งอีเมลใดๆ ในรอบนี้** — ไม่แจ้งผู้ดูแลเมื่อมีคนรออนุมัติ และไม่แจ้งผู้สมัคร
  เมื่อผลออก · การแจ้งผู้สมัครถูกแยกไปเป็น **เฟสที่ 4** (หัวข้อ 6) เพราะต้องเพิ่ม
  ผู้ให้บริการภายนอกและแก้เอกสารทางกฎหมายพร้อมกัน
- ไม่มีป้ายนับจำนวนคิวบนแถบเมนู — `navItems.ts` เป็นข้อมูลคงที่ การใส่ตัวนับ
  ต้องให้แถบเมนูดึงข้อมูล ซึ่งเกินขอบเขตรอบนี้
- ผู้ดูแลเลือกสิทธิ์ตอนอนุมัติไม่ได้ อนุมัติแล้วได้ `member` เสมอ
  การเลื่อนสิทธิ์ยังเป็นงานแยกที่ช่องเลือกสิทธิ์เดิม

## การตัดสินใจที่บันทึกไว้

| เรื่อง | เลือก | ที่ไม่เลือกและเพราะอะไร |
|---|---|---|
| ใครเริ่มกระบวนการ | **สมัครเองได้ แต่ใช้ไม่ได้จนกว่าจะอนุมัติ** | ผู้ดูแลสร้างบัญชีให้แล้วส่งคำเชิญ — ปลอดภัยกว่าเพราะไม่มีประตูสมัครเปิดอยู่ แต่ผู้ดูแลต้องรู้อีเมลล่วงหน้าและพิมพ์เอง |
| สิทธิ์ตอนอนุมัติ | **ได้ `member` เสมอ** | ให้เลือกสิทธิ์ตอนอนุมัติ — จบในขั้นตอนเดียวแต่ปนสองงานเข้าด้วยกัน |
| การปฏิเสธ | **ทำเครื่องหมายไว้ บัญชียังอยู่** | ลบบัญชีทิ้ง — ไม่เหลือร่องรอยว่าเคยปฏิเสธใคร และชนปัญหาที่พบมาแล้วว่าอีเมลที่ถูกลบสมัครใหม่ไม่ได้ · ไม่มีปุ่มปฏิเสธเลย — คิวจะโตขึ้นเรื่อยๆ โดยไม่มีทางลด |
| เก็บสถานะอย่างไร | **คอลัมน์ใหม่ `profiles.status`** | เพิ่มค่าเข้า `user_role` enum — ปนสองความหมาย และช่องเลือกสิทธิ์จะมีค่าที่ไม่มีความหมายให้เลือก |
| Shortlist เขียนข้อมูลที่ไหน | **คงการเขียนผ่าน PostgREST ด้วย anon key ภายใต้ RLS** | ย้ายไป API route ด้วย service-role — สม่ำเสมอกับอีก 20 route แต่ **ทำให้ด่านอ่อนลง** เพราะ service-role bypass RLS ทั้งหมด การกั้นจะเหลือแค่ `.eq('owner_id', ...)` ที่ต้องเขียนเองทุกครั้ง |
| ปุ่มบันทึกอยู่ที่ไหน | **หน้ารายละเอียด + ผลการค้นหา + รายชื่อในหน้างาน** | หน้ารายละเอียดที่เดียว — แก้หน้าตาแต่ไม่แก้ปัญหา เพราะจุดที่คนตัดสินใจเก็บคนไว้คือตอนกวาดสายตาดูผลการค้นหา |

## 1. การอนุมัติบัญชี

### 1.1 ฐานข้อมูล

```sql
create type account_status as enum ('pending', 'approved', 'rejected');

alter table profiles
  add column status account_status not null default 'pending';

update profiles set status = 'approved';
```

**ลำดับสองบรรทัดนี้สลับไม่ได้** `default 'pending'` ทำให้คนที่สมัครหลังจากนี้ติดคิวเอง
โดยไม่ต้องแก้ trigger `handle_new_user` (migration 002) ซึ่งใส่แค่ `id, display_name, role`
ส่วน `update` กวาดแถวเดิมให้ผ่านทั้งหมด **ถ้ารัน `update` ก่อนเพิ่มคอลัมน์ หรือลืมรัน
ผู้ดูแลจะล็อกตัวเองออกจากระบบและกู้ได้ทางเดียวคือ SQL editor**

**ห้ามเพิ่ม `status` เข้า `grant update` ของ migration 019** คอลัมน์ใหม่ไม่ได้สิทธิ์เขียน
โดยอัตโนมัติ ซึ่งเป็นพฤติกรรมที่ migration นั้นออกแบบไว้แล้ว ถ้าเผลอเพิ่ม ผู้ใช้ทุกคน
จะยิง `PATCH /rest/v1/profiles?id=eq.<ตัวเอง>` ด้วย `{"status":"approved"}` เพื่ออนุมัติตัวเองได้

### 1.2 ด่านตรวจ

`decideAccess` รับ `status` เพิ่ม และตรวจ**หลัง** role

```
read-failed → no-profile → bad-role → pending → rejected → allowed
```

**ลำดับนี้มีความหมาย** แถวที่ `role` เป็นค่าแปลกปลอม**และ** `status` เป็น `pending`
ต้องคืน `bad-role` ไม่ใช่ `pending` — ไม่งั้นบัญชีที่ข้อมูลเสียจะถูกรายงานว่า
"รออนุมัติ" แล้วผู้ดูแลจะกดอนุมัติให้บัญชีที่พัง

ข้อความที่ผู้ใช้เห็น เพิ่มใน `accessDeniedMessage`

| เหตุผล | ข้อความ |
|---|---|
| `pending` | บัญชีนี้รอการอนุมัติจากผู้ดูแลระบบ กรุณาติดต่อผู้ดูแลหากรอเกินสมควร |
| `rejected` | บัญชีนี้ไม่ได้รับอนุมัติให้ใช้งาน กรุณาติดต่อผู้ดูแลระบบ |

**`getSession()` ยังคืน `null` เหมือนเดิม** ผู้เรียกทั้ง 40 จุดจึงไม่ต้องแก้ หน้า `/login`
เป็นที่เดียวที่อธิบายเหตุผล ตามรูปแบบที่ระบบใช้อยู่

### 1.3 `/auth/confirm` ต้องแก้ด้วย

หน้านี้ล็อกอินให้แล้วพาไป `/dashboard` ทันทีหลังยืนยันอีเมล **คนที่เพิ่งยืนยันจะถูกเด้ง
กลับโดยไม่รู้สาเหตุ** ต้องให้ตรวจสถานะก่อน แล้วแสดงข้อความรออนุมัติแทนการ redirect

### 1.4 หน้าจอผู้ดูแล

เพิ่มส่วน **"บัญชีรออนุมัติ"** ไว้บนสุดของ `/admin/users` ไม่แยกหน้าใหม่ — หน้าแยก
ต้องมีคนจำว่าต้องไปดู ส่วนนี้อยู่ในหน้าที่ผู้ดูแลเปิดอยู่แล้ว และซ่อนตัวเองเมื่อคิวว่าง

แต่ละแถว: อีเมล · วันที่สมัคร · ปุ่ม **อนุมัติ** / **ปฏิเสธ**

ตารางผู้ใช้หลักด้านล่างเพิ่มคอลัมน์สถานะ เพื่อให้เห็นบัญชีที่ถูกปฏิเสธไปแล้ว
และเปลี่ยนใจอนุมัติทีหลังได้

### 1.5 API

`POST /api/admin/users/[id]/status` รับ `{ status: 'approved' | 'rejected' }`

- กั้น `admin` — ปฏิเสธ**ก่อน**แตะฐานข้อมูล
- บันทึกลง `activity_log` ด้วย action `account_status` และ `entity_type` `user`
  **ไม่ต้อง migration** เพราะสองคอลัมน์นั้นเป็น `text` เปล่าไม่มี CHECK
- ไม่ส่งข้อความ Postgres ดิบกลับไป `console.error` ฝั่งเซิร์ฟเวอร์เก็บข้อความเต็ม

## 2. Shortlist

### 2.1 `SaveToShortlist` แทน `AddToShortlist`

ปุ่ม **บันทึก** ติดกับผู้สมัครแต่ละคน กดแล้วเปิดแผงที่แสดงรายการทั้งหมดของผู้ใช้
พร้อมช่องติ๊ก

- ติ๊ก = เพิ่ม · เอาติ๊กออก = ลบ **มีผลทันที ไม่มีปุ่มยืนยัน**
- ล่างสุดมีช่องพิมพ์ชื่อ + ปุ่มสร้างรายการใหม่ ซึ่งสร้างแล้วติ๊กให้เลย

**สองสถานะของปุ่ม** — ยังไม่อยู่ในรายการใดเลยแสดงว่า `บันทึก` แบบเส้นขอบ ·
อยู่ในรายการอย่างน้อยหนึ่งรายการแล้วแสดงว่า `บันทึกแล้ว` แบบพื้นทึบ
ความต่างต้องอ่านออกโดยไม่ต้องพึ่งสีอย่างเดียว เพราะผู้ใช้บางคนแยกสีได้ไม่ชัด

ใช้คอมโพเนนต์เดียวกันทั้งสามที่: `/candidates/[id]` · `/search` · `/jobs/[id]`

### 2.2 การดึงสถานะ

ต้องใช้ข้อมูลสองชุด

**ชุดที่ 1 — รายการ Shortlist ทั้งหมดของผู้ใช้** ดึงครั้งเดียวต่อหน้า ใช้ร่วมกันทุกปุ่ม

```
select id, name from shortlists order by created_at
```

**ชุดที่ 2 — ความเป็นสมาชิก** ของผู้สมัครที่แสดงอยู่บนหน้านั้น ดึงเป็นชุดเดียว
ไม่ถามทีละคน

```
select shortlist_id, candidate_id from shortlist_candidates
where candidate_id in (<คนที่แสดงอยู่>)
```

RLS กรองให้เหลือเฉพาะรายการของเจ้าของอยู่แล้วทั้งสองคำขอ รวมเพิ่มสองคำขอต่อหน้า
ซึ่งเทียบกับการค้นหาเชิงความหมายที่หน้านั้นทำอยู่แล้วถือว่าไม่มีนัยสำคัญ

### 2.3 หน้า `/shortlists`

เพิ่มสามอย่าง

- **แก้ชื่อ** คลิกที่ชื่อแล้วแก้ในที่
- **ลบรายการ** มีกล่องยืนยันที่**บอกจำนวนผู้สมัครที่จะหายไปด้วย**
- **เอาผู้สมัครออก** มีอยู่แล้ว คงไว้

### 2.4 เพดานความยาวชื่อ

เพราะเขียนผ่าน PostgREST ตรง จึงไม่มี API route ให้ตรวจค่าฝั่งเซิร์ฟเวอร์ —
ช่องเดียวกับที่ UAT จับได้ใน ST-13 เรื่องชื่อที่แสดงไม่มีเพดาน

แก้ด้วยข้อจำกัดที่ฐานข้อมูล

```sql
alter table shortlists add constraint shortlists_name_len
  check (char_length(trim(name)) between 1 and 60);
```

**ฐานข้อมูลบังคับเอง จึงกันได้ทุกเส้นทาง** ไม่ว่าจะยิงจากหน้าจอหรือยิง PostgREST ตรง
ได้ผลเท่ากับมี API route โดยไม่เสียข้อดีของ RLS · `trim` อยู่ข้างในเพราะชื่อที่เป็น
ช่องว่างล้วนต้องไม่ผ่าน เหมือนที่ ST-04 ทดสอบกับชื่อที่แสดง

### 2.5 ลบคอลัมน์ `note`

```sql
alter table shortlist_candidates drop column note;
```

**ตรวจก่อนลบ** เพราะเอาคืนไม่ได้

```sql
select count(*) from shortlist_candidates
where note is not null and trim(note) <> '';
```

ได้ 0 ค่อยลบ — ยืนยันแล้วว่าไม่มีโค้ดไหนอ่านหรือเขียนคอลัมน์นี้ แต่ถ้าเคยมีใคร
กรอกผ่าน SQL editor ด้วยมือ ตัวเลขจะไม่เป็นศูนย์

กฎ "migration ต้องเป็นแบบเพิ่ม" ใน `CLAUDE.md` เขียนไว้เพื่อปกป้องตาราง `jobs`
โดยเฉพาะ และมีแบบอย่างแล้วใน migration 011 ที่ลบตาราง `resumes` กับ `matches`
ด้วยเหตุผลเดียวกันคือไม่มีใครอ้างถึง · เหตุผลที่ลบคุ้มกว่าเก็บคือเล่มมีบท
Data Dictionary ที่ต้องอธิบายทุกคอลัมน์

## 5. การทดสอบ

### การอนุมัติบัญชี

**Unit — `decideAccess`** ตรวจ**ลำดับการตัดสิน** ไม่ใช่แค่ผลลัพธ์ กรณีสำคัญคือ
แถวที่ role เพี้ยนและ status เป็น pending พร้อมกัน ต้องคืน `bad-role`

**Integration — migration 022** ตามแบบ `019_lock_profile_columns.int.test.ts`
คือสร้างบัญชีจริงแล้วยิง PostgREST ตรงด้วย anon key ไม่ใช่ดูจากหน้าจอ

- บัญชีใหม่ได้ `status = 'pending'` โดยไม่ต้องแก้ trigger
- `PATCH profiles` ด้วย `{"status":"approved"}` ผ่าน anon key **ต้องไม่สำเร็จ**
- ตรวจค่าในฐานซ้ำหลังยิง ไม่เชื่อค่า `error` อย่างเดียว

**Route** — `member` และ `data_manager` ต้อง**ไม่ทำให้เกิดการเขียนลงฐาน**
ไม่ใช่แค่ได้ 403 · role ที่ enum ไม่รู้จักต้องปิดประตู

### Shortlist

**Integration — ข้อจำกัดความยาว** ทดสอบ 60 ผ่าน · 61 ไม่ผ่าน · ช่องว่างล้วนไม่ผ่าน

## 6. เฟสที่ 4 — แจ้งผลทางอีเมล (ยังไม่ทำในรอบนี้)

แจ้งผู้สมัครทางอีเมลที่ใช้สมัคร **ทั้งตอนอนุมัติและตอนปฏิเสธ**

### ทำไมแยกเป็นเฟสหลัง

สามข้อแรกใช้งานได้เต็มที่โดยไม่มีอีเมล ผู้ใช้เห็นสถานะตอนล็อกอินอยู่แล้ว ส่วนเฟสนี้
เพิ่ม **บัญชีผู้ให้บริการใหม่ · secret ใหม่ · การยืนยันโดเมน · และการแก้เอกสารทางกฎหมาย**
ซึ่งไม่มีอะไรเกี่ยวกับตรรกะการอนุมัติเลย

### ข้อจำกัดที่ทำให้ต้องใช้ผู้ให้บริการภายนอก

**Supabase Auth ส่งได้เฉพาะอีเมลของกระบวนการยืนยันตัวตน** (ยืนยันการสมัคร · เชิญผู้ใช้ ·
ลิงก์เข้าระบบ · เปลี่ยนอีเมล · รีเซ็ตรหัสผ่าน) **ไม่มี API ให้ส่งอีเมลทั่วไป**

และ `authMessages.ts` บันทึกไว้แล้วว่าโควตา SMTP ของ free tier ต่ำมากจน UAT เจอ
`email rate limit exceeded` จริง — ไม่ควรฝากงานส่งอีเมลเพิ่มไว้กับช่องทางนั้นแม้ทำได้

### ข้อกำหนดเมื่อลงมือทำ

**ส่งหลังบันทึกสถานะสำเร็จเท่านั้น และการส่งที่ล้มเหลวห้ามทำให้ทั้งคำขอล้ม**
ผู้ดูแลกดอนุมัติไปแล้วจริง การตอบว่า "ล้มเหลว" ตอนนั้นจะผิด — หลักเดียวกับ `logActivity`
และการล้าง cache ตอนแก้งานใน Phase 9

**การส่งที่ล้มเหลวต้อง `console.error`** ไม่งั้นเงียบสนิท แล้ววันหนึ่งจะพบว่าไม่มีใคร
ได้รับอีเมลมาเป็นเดือนโดยไม่มีสัญญาณใดเลย

**แยกการส่งออกเป็นโมดูลของตัวเอง** (เช่น `lib/email/send.ts`) เพื่อให้ route test
แทนที่ได้ และทดสอบได้ว่า "ส่งล้มแล้ว route ยังตอบสำเร็จ" ซึ่งเป็นพฤติกรรมที่ต้องการ

**secret ใหม่ลงสองที่** — `.env` บนเครื่อง และ Vercel · **ไม่ต้องลง GitHub Actions**
เพราะ workflow ไม่เกี่ยวกับการอนุมัติบัญชี

**ต้องยืนยันโดเมนกับผู้ให้บริการ** ไม่งั้นอีเมลไปลงถังขยะ ซึ่งแย่กว่าไม่ส่งเลย
เพราะผู้ใช้จะเชื่อว่าระบบไม่ตอบสนอง

### ⚠️ ผลพ่วงด้านกฎหมายที่ต้องทำพร้อมกัน

**เพิ่มผู้ให้บริการอีเมลเข้า `PROCESSORS` ใน `lib/legal/meta.ts`**

`CLAUDE.md` ระบุว่า "เพิ่มบริการภายนอกที่แตะข้อมูลส่วนบุคคลเมื่อไร ต้องเพิ่มใน
`PROCESSORS`" และทั้งสามรายที่มีอยู่ (Supabase · Gemini · Vercel) อยู่นอกประเทศไทย
จึงเป็น**การโอนข้อมูลข้ามพรมแดนที่ต้องแจ้ง** ผู้ให้บริการอีเมลก็อยู่นอกประเทศเช่นกัน

**หน้า `/privacy` ที่เผยแพร่อยู่จะเปลี่ยนตามทันที** เพราะอ่านค่าจากไฟล์นั้น —
ถือเป็นการแก้นโยบายที่ประกาศไว้แล้ว ไม่ใช่แค่แก้โค้ด

ตัวการส่งอีเมลเองไม่มีปัญหา — เป็นอีเมลที่เจ้าตัวกรอกมาเอง และการแจ้งผลการสมัคร
คือการใช้ตามวัตถุประสงค์ที่เก็บมา

### เนื้อความ

สองแม่แบบ

| กรณี | สาระที่ต้องมี |
|---|---|
| อนุมัติ | บัญชีใช้งานได้แล้ว · ลิงก์ไปหน้าเข้าสู่ระบบ |
| ปฏิเสธ | บัญชีไม่ได้รับอนุมัติ · **ช่องทางติดต่อผู้ดูแล** |

**อีเมลปฏิเสธต้องบอกช่องทางติดต่อเสมอ** การแจ้งว่าไม่ผ่านโดยไม่บอกว่าจะถามใครต่อ
แย่กว่าไม่แจ้งเลย — หลักเดียวกับที่ `lib/help/contact.test.ts` ดักไว้ว่าหน้าที่บอก
ช่องทางติดต่อที่ไม่มีอยู่จริงแย่กว่าไม่มีหน้านั้น

## 7. ความเสี่ยงและข้อจำกัดที่รู้ตัว

**ประตูสมัครยังเปิดอยู่** ใครก็สร้างบัญชีรออนุมัติได้ คิวอาจถูกถมด้วยการสมัครที่
ไม่พึงประสงค์ ปุ่มปฏิเสธช่วยให้คิวลดลงได้แต่ไม่ได้กันการสมัคร ถ้าวันหนึ่งเป็นปัญหาจริง
ทางแก้คือปิดสวิตช์ที่ Supabase → Authentication → Providers → Email →
"Allow new users to sign up" ซึ่ง**เป็นที่เดียวที่ปิดการสมัครได้จริง** การลบหน้า
`/signup` ไม่ช่วย เพราะ anon key เป็นค่าสาธารณะและ `POST /auth/v1/signup` ยังทำงาน

**ผู้ดูแลต้องเข้ามาดูเอง** ไม่มีการแจ้งเตือน คนที่รออนุมัติอาจรอนานโดยไม่มีใครรู้

**ยังไม่ได้ตัดสินใจเรื่องการลบบัญชีที่ถูกปฏิเสธ** บัญชีเหล่านั้นอยู่ในระบบตลอดไป
ถ้าต้องการลบตามคำขอของเจ้าของข้อมูลตาม PDPA มาตรา 33 ยังต้องทำผ่าน Supabase ด้วยมือ

**ชื่อ Shortlist 60 ตัวอักษรเป็นตัวเลขที่ตั้งเอง** ไม่ได้มาจากข้อจำกัดของฐานข้อมูล
เหมือนกรณี `jobs.title` ที่เป็น `varchar(255)` — ถ้าผู้ใช้บ่นว่าสั้นไป เปลี่ยนได้
แต่ต้องแก้ทั้ง constraint และเลขที่ hardcode ไว้ในเทสต์
