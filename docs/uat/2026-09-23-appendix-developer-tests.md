## ภาคผนวก ก — เคสทดสอบที่ดำเนินการโดยผู้พัฒนา

เอกสารส่วนหลักประกอบด้วยเคสทดสอบที่ผู้ใช้ทั่วไปดำเนินการได้ด้วยเบราว์เซอร์เพียงอย่างเดียว อย่างไรก็ตาม การทดสอบระบบยังมีอีกเจ็ดเคสที่ไม่สามารถดำเนินการผ่านหน้าจอได้ จึงแยกมาไว้ในภาคผนวกนี้ และผู้พัฒนาได้ดำเนินการทดสอบไปแล้วระหว่างวันที่ 15 ถึง 18 กันยายน 2569

**เหตุผลที่ต้องแยก** เคสทั้งเจ็ดตรวจสอบการทำงานของระบบในระดับที่อยู่หลังหน้าจอ กล่าวคือ ตรวจสอบว่าเมื่อมีการส่งคำขอไปยังระบบโดยตรงโดยไม่ผ่านส่วนติดต่อผู้ใช้ ระบบยังคงปฏิเสธคำขอที่ไม่ถูกต้องหรือไม่ การทดสอบเพียงว่า "กดปุ่มในหน้าเว็บไม่ได้" ไม่ถือเป็นการทดสอบมาตรการควบคุมที่แท้จริง เนื่องจากหน้าจอเป็นเพียงด่านแรกซึ่งผู้ใช้สามารถข้ามไปได้ด้วยเครื่องมือสำหรับนักพัฒนาที่ติดมากับเบราว์เซอร์ทุกตัว

**วิธีดำเนินการ** เข้าสู่ระบบด้วยบัญชีที่แต่ละเคสกำหนด เปิดเครื่องมือสำหรับนักพัฒนา (DevTools) แล้วส่งคำขอไปยังระบบโดยตรงจากหน้าต่าง Console โดยคุกกี้ของเซสชันจะติดไปกับคำขอโดยอัตโนมัติ จากนั้นพิจารณาผลสองส่วน คือ รหัสสถานะ (status code) ที่ระบบตอบกลับ และข้อความที่ส่งกลับมา

### ตารางผลการทดสอบ

| รหัส | ส่วนที่ทดสอบ | สิ่งที่ตรวจสอบ | ผลการทดสอบ |
|---|---|---|---|
| AD-02 | จัดการผู้ใช้ · การป้องกันการลดสิทธิ์ตนเอง | ผู้ดูแลระบบส่งคำขอลดสิทธิ์ของตนเองโดยตรง | **ผ่าน** — ระบบตอบกลับสถานะ 400 พร้อมข้อความปฏิเสธ และสิทธิ์ในฐานข้อมูลไม่เปลี่ยนแปลง |
| ST-11 | ประเมินตัวเอง · สิทธิ์ของเจ้าของข้อมูล | ผู้ใช้รายหนึ่งพยายามลบข้อมูลประเมินของผู้ใช้อีกราย | **ผ่าน** — ระบบตอบกลับสถานะ 404 มิใช่ 403 และข้อมูลของเจ้าของยังอยู่ครบถ้วน |
| ST-12 | ประเมินตัวเอง · สิทธิ์ของเจ้าของข้อมูล | ผู้ใช้รายหนึ่งพยายามอ่านผลประเมินของผู้ใช้อีกราย | **ผ่าน** — ระบบตอบกลับสถานะ 404 และไม่ส่งคะแนนหรือข้อความวิเคราะห์ใดกลับมา |
| SR-05 | ค้นหา · การทำงานเมื่อบริการ AI ขัดข้อง | ค้นหาผู้สมัครในขณะที่บริการ AI ใช้งานไม่ได้ | **ผ่าน** — ระบบยังค้นหาและแสดงผลลัพธ์ได้ เพียงแต่ไม่มีการแยกเงื่อนไขเป็นตัวกรองอัตโนมัติ |
| SA-02 | ประเมินตัวเอง · การตรวจชนิดไฟล์ | อัปโหลดไฟล์ที่มิใช่ PDF โดยส่งคำขอตรง | **ผ่าน** — ระบบตอบกลับสถานะ 400 พร้อมข้อความว่ารองรับเฉพาะไฟล์ PDF และปฏิเสธก่อนส่งไฟล์ต่อให้บริการ AI จึงไม่เกิดค่าใช้จ่าย |
| JB-11 | ตำแหน่งงาน · เพดานความยาวข้อความ | ส่งชื่อตำแหน่งงานความยาว 256 ตัวอักษร ซึ่งเกินเพดานของฐานข้อมูลหนึ่งตัวอักษร | **ผ่าน** — ระบบตอบกลับสถานะ 400 พร้อมข้อความที่ระบุเพดานจริง มิใช่ข้อความแจ้งข้อผิดพลาดทั่วไป |
| ST-13 | ตั้งค่า · เพดานความยาวข้อความ | ส่งชื่อที่แสดงความยาว 255 ตัวอักษร ซึ่งเกินเพดานของฐานข้อมูลหนึ่งตัวอักษร โดยส่งคำขอตรงด้วยกุญแจสาธารณะ | **ผ่าน** — ฐานข้อมูลปฏิเสธคำขอ และค่าที่บันทึกไว้เดิมไม่เปลี่ยนแปลง · ดูคำอธิบายในหัวข้อถัดไป |

**สรุป** ผ่านทั้ง 7 เคส

**หมายเหตุด้านวิธีการ** เคส AD-02, ST-11 และ ST-12 ต้องใช้รหัสประจำตัวของบัญชีผู้ใช้ในการส่งคำขอ ซึ่งระบบมิได้แสดงค่าดังกล่าวไว้ที่ใดในส่วนติดต่อผู้ใช้ ผู้ทดสอบจึงต้องเรียกดูจากฐานข้อมูลโดยตรง ข้อเท็จจริงนี้มิได้ทำให้มาตรการควบคุมแข็งแรงขึ้นแต่อย่างใด เนื่องจากการไม่แสดงค่าใดค่าหนึ่งมิใช่การควบคุมการเข้าถึง แต่เป็นเพียงการทำให้ค้นหาได้ยากขึ้นเท่านั้น จึงยังจำเป็นต้องมีการตรวจสอบสิทธิ์ที่ฝั่งเซิร์ฟเวอร์เสมอ ซึ่งเป็นสิ่งที่ทั้งสามเคสยืนยันว่ามีอยู่จริง

### ST-13 — ข้อบกพร่องที่ตรวจพบ แก้ไข และทดสอบซ้ำ

**การทดสอบรอบแรกเมื่อ 23 กันยายน 2569 ไม่ผ่าน** เคสนี้ตรวจสอบว่าระบบจำกัดความยาวของชื่อที่แสดง (display name) ในระดับเซิร์ฟเวอร์หรือไม่ ผลการตรวจสอบสามชั้นพบว่า**ไม่มีมาตรการจำกัดความยาวในระดับเซิร์ฟเวอร์เลย** กล่าวคือ ไม่มีเส้นทาง API ที่ทำหน้าที่บันทึกค่านี้ คอลัมน์ในฐานข้อมูลเป็นชนิดข้อความที่ไม่ได้กำหนดความยาวสูงสุด และไม่มีเงื่อนไขตรวจสอบค่าที่ระดับฐานข้อมูล มาตรการเดียวที่มีอยู่คือคุณสมบัติจำกัดความยาวของช่องกรอกในหน้าจอ ซึ่งป้องกันได้เฉพาะการพิมพ์และการวางข้อความเท่านั้น

**ข้อสังเกตที่สำคัญคือการเปรียบเทียบกับเคส JB-11** ทั้งสองเคสตรวจสอบเรื่องเดียวกัน คือเพดานความยาวของข้อความที่ผู้ใช้กรอก และทั้งสองหน้าจอแสดงพฤติกรรมเหมือนกันทุกประการเมื่อทดสอบผ่านเบราว์เซอร์ตามปกติ แต่เมื่อส่งคำขอตรงกลับได้ผลต่างกันโดยสิ้นเชิง เนื่องจากการสร้างตำแหน่งงานส่งผ่านเส้นทาง API ที่มีการตรวจสอบค่าอยู่จริง ในขณะที่การบันทึกชื่อที่แสดงเขียนลงฐานข้อมูลโดยตรงโดยไม่ผ่านการตรวจสอบใด **ข้อเท็จจริงนี้แสดงให้เห็นว่า การทดสอบผ่านหน้าจอเพียงอย่างเดียวไม่สามารถแยกความแตกต่างระหว่างระบบที่มีมาตรการควบคุมกับระบบที่ไม่มีได้** ซึ่งเป็นเหตุผลหลักที่เอกสารฉบับนี้แยกการทดสอบระดับเซิร์ฟเวอร์ออกมาต่างหาก

**การแก้ไขเมื่อ 14 ตุลาคม 2569** เพิ่มเงื่อนไขตรวจสอบความยาวที่ระดับฐานข้อมูล (migration 023) ซึ่งเป็นแนวทางแรกจากสองแนวทางที่บันทึกไว้ในรอบแรก เลือกแนวทางนี้เพราะการบันทึกชื่อที่แสดงเขียนลงฐานข้อมูลโดยตรง การเพิ่มเงื่อนไขที่ระดับฐานจึงครอบคลุมทุกเส้นทางที่เข้าถึงค่านี้ได้ รวมถึงคำขอที่ส่งตรงโดยไม่ผ่านส่วนติดต่อผู้ใช้

**เพดานที่ระดับฐานข้อมูลกำหนดไว้ที่ 254 ตัวอักษร ซึ่งต่างจากเพดาน 60 ตัวอักษรของช่องกรอก และความต่างนี้เป็นไปโดยเจตนา** เนื่องจากระบบกำหนดค่าเริ่มต้นของชื่อที่แสดงเป็นที่อยู่อีเมลของผู้ใช้ขณะสมัครสมาชิก การตั้งเพดานที่ระดับฐานให้เท่ากับ 60 ตัวอักษรจะทำให้ผู้ที่สมัครด้วยที่อยู่อีเมลยาวกว่านั้นไม่สามารถสมัครสมาชิกได้เลย ค่า 254 จึงอ้างอิงจากความยาวสูงสุดของที่อยู่อีเมลตามมาตรฐาน RFC 5321 **เพดานทั้งสองระดับทำหน้าที่ต่างกัน** คือเพดานที่ช่องกรอกเป็นกฎด้านความเรียบร้อยของการแสดงผล ส่วนเพดานที่ฐานข้อมูลเป็นมาตรการป้องกันการใช้งานผิดวัตถุประสงค์

**การทดสอบซ้ำ** ดำเนินการด้วยชุดทดสอบอัตโนมัติที่สร้างบัญชีผู้ใช้จริง เข้าสู่ระบบด้วยกุญแจสาธารณะ แล้วส่งคำขอแก้ไขข้อมูลตรงไปยังฐานข้อมูลโดยไม่ผ่านส่วนติดต่อผู้ใช้ **ซึ่งเป็นเส้นทางเดียวกับที่ใช้ตรวจพบข้อบกพร่องในรอบแรก** ผลการทดสอบก่อนการแก้ไขไม่ผ่าน 2 ข้อ และผ่านทั้ง 4 ข้อภายหลังการแก้ไข ยืนยันว่าชุดทดสอบตรวจจับข้อบกพร่องนี้ได้จริง มิใช่ผ่านเพราะไม่ได้ตรวจสอบสิ่งใด

**เหตุผลที่บันทึกข้อบกพร่องและกระบวนการแก้ไขไว้ในเอกสาร** ผลการทดสอบที่ผ่านทุกเคสโดยไม่มีข้อยกเว้นมิได้เป็นเครื่องยืนยันว่าระบบไม่มีข้อบกพร่อง แต่มักเป็นเครื่องบ่งชี้ว่าการทดสอบยังไม่ครอบคลุมเพียงพอ การรายงานข้อบกพร่องที่ตรวจพบพร้อมการวิเคราะห์สาเหตุ แนวทางแก้ไขที่เลือกพร้อมเหตุผล และหลักฐานการทดสอบซ้ำ จึงมีคุณค่าต่อการประเมินระบบมากกว่าการละเว้นไม่กล่าวถึง
